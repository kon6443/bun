# 플로우 기반 QA 리뷰 (백엔드 — 프론트 대조는 프론트 세션)

모든 판단은 코드를 직접 확인한 근거로만 한다. 추측 금지.

> 백·프 2세션 체제(`CLAUDE.md` "세션 운영"): 이 리뷰는 **백엔드 코드만** 읽는다. 프론트 소스를 grep·Read하지 않는다 — 프론트 사용처·타입·소켓 핸들러 대조가 필요하면 스킬 `next-bun`의 양식으로 **프론트 세션에 질의**하고, 답(`파일:라인 + 인용`)을 결과에 "프론트 세션 확인"으로 표기한다.

## 1. 변경 파일 파악

- `git diff --name-only`(필요하면 `--cached`·`<base>..HEAD`)로 변경 파일을 본다. pathspec에 `'src/**/*.ts'`를 쓰지 않는다 — `src/` 직속 파일이 빠진다. `-- src/` 또는 `-- ':(glob)src/**/*.ts'`.
- 추가·수정된 함수, API, 타입, 이벤트를 식별한다.

## 2. grep 전수 확인

- 변경된 이름으로 **백엔드** 전체를 grep한다. 프론트 사용처는 프론트 세션에 질의한다(직접 grep하지 않는다).
- 같은 함수가 여러 곳에서 호출되면 중복·불필요 여부를 교차 비교한다.
- 파일 부분 읽기(offset/limit)만으로 "전체 정상"이라 판단하지 않는다.
- **부정 판정**("사용처 없음", "영향 없음")은 탐색 범위를 문장에 밝히고, 문자열 grep 외에 성격이 다른 경로(라우트 정의·타입 정의·import 추적) 하나 이상으로 확인했을 때만 쓴다. 아니면 "X 범위에서 찾지 못함(미확인)".

## 3. 플로우 리스트업

유저 액션 기준으로 분류한다: `유저 액션 → (프론트 핸들러 — 프론트 세션 확인) → API 호출 → Controller → Service → DB → 소켓 emit`

## 4. 플로우별 추적 검증

1. **중복 호출** — 같은 API·함수가 불필요하게 여러 번 호출되지 않는가
2. **소켓 이벤트** — emit 횟수, 페이로드 필드, self-event 필터링, 토스트 중복
3. **타입 일치** — Entity → 쿼리 select → 서비스 매핑 → DTO → 소켓 페이로드 체인을 1:1 대조. 프론트 타입과의 대조는 프론트 세션 답으로
4. **필드 누락** — 새 필드가 위 체인 전체에 있는가 (`forbidNonWhitelisted`라 요청 필드가 어긋나면 422)
5. **인가** — 팀 멤버십·역할 검증이 서비스/컨트롤러에 있는가 (Guard는 인증까지만)
6. **기능 정합성** — 의도한 데이터만 바뀌고 부수효과가 없는가

## 5. Swagger

변경 엔드포인트의 `@ApiOperation` · `@ApiProperty` · `@ApiQuery`/`@ApiParam` · 응답 DTO · 공통 에러 데코레이터.

## 6. 중복 코드

같은 패턴이 3곳 이상이면 공통 함수 추출을 제안한다. 오버엔지니어링 금지.

## 7. 빌드 검증

- 백엔드: `pnpm ci:core`
- 프론트: 프론트 변경이 함께 있으면 프론트 세션이 자기 레포 통합 명령으로 검증해 보고한다(메인이 돌리지 않는다). dev 서버가 도는 디렉토리에서 build를 돌리지 않는다(`docs/lessons.md`)
