## D-001 — 요구사항 원문 (2026-10-21)
- **상태**: ✅ 확정 (사용자 지시)
- **결정**:
  - BNB에 피드백 칸을 추가하고, **로그인한 유저만** 업로드할 수 있다.
  - 마이페이지에서 **내 피드백**을 확인할 수 있다.
  - 유저 입력은 제목·내용·카테고리 정도 — 추가 필드는 추천받는다.
  - 카테고리는 기능 추가·에러 리포트·개선 요청 등 — 추천받는다.
  - 태스크 파일 SSOT를 유지하며 진행한다. **아직 실제 구현은 하지 않는다.**
- **영향**: 백엔드(신규 테이블·REST) + 프론트(BNB·작성 폼·마이페이지).

## D-002 — 세션·브랜치 구성 (2026-10-21)

## D-003 — 카테고리 5종 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q4, 2026-10-21)
- **결정(안)**: 코드값(영문, DB 저장) ↔ 표시명
  | 코드 | 표시명 | 의도 |
  |---|---|---|
  | `FEATURE` | 기능 추가 | 없는 기능 요청 |
  | `BUG` | 버그 리포트 | 에러·오작동 — 자동 메타(D-004) 첨부 대상 |
  | `IMPROVEMENT` | 개선 요청 | 있는 기능의 사용성·디자인·성능 |
  | `QUESTION` | 문의 | 사용법·계정 문의 |
  | `OTHER` | 기타 | 칭찬·그 외 |
- **근거**: 처리 주체가 달라지는 경계로만 나눈다(개발 백로그 / 버그 수정 / 응대). 5개를 넘으면 사용자가 고르는 데 망설인다. "디자인/UX"는 개선 요청에 포함.
- **저장 방식**: `VARCHAR2(20)` 코드값 + `CHECK` 제약 + 백엔드 enum. 별도 코드 테이블은 두지 않는다(값 추가 시 마이그레이션 1개로 CHECK 교체 — 빈도 낮음).
- **버린 대안**: 카테고리 테이블(관리 화면 없이 이득 없음) · 자유 입력 태그(통계 불가)

## D-004 — 필드 구성 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q4, 2026-10-21)
- **결정(안)**: 정본은 DESIGN.md §1
  - 유저 입력: 제목(1~100자) · 내용(1~5,000자) · 카테고리(D-003)
  - 처리 루프: `STATUS`(`RECEIVED` 접수 → `IN_PROGRESS` 검토 중 → `DONE` 반영 완료 / `REJECTED` 반려) · `ADMIN_REPLY`(운영자 답변) · `REPLIED_DATE`
  - 자동 메타(유저가 입력하지 않음, 프론트가 붙임): `PAGE_PATH`(작성 직전 화면) · `USER_AGENT` · `APP_VERSION`
  - 공통: `CREATED_DATE` · `UPDATED_DATE` · `IS_DELETED`
- **근거**: 상태·답변이 없으면 마이페이지 "내 피드백"이 보낸 편지함에 그쳐 재방문 이유가 없다. 버그 리포트는 환경 정보 없이는 재현이 어렵다 — 유저에게 묻지 않고 자동으로 받는다.
- **버린 대안**: 연락처·이메일 입력(카카오 계정으로 이미 식별) · 별점/NPS(목적이 다름 — 후속 아이디어로만 기록)

## D-008 — 운영자 확인: 디스코드 + 텔레그램 알림, 처리는 SQL (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q1)
- **결정**: 작성 직후 운영자 채널 2곳에 알림을 보낸다 — 디스코드 `DiscordService.sendWebhookMessage(url, …)`(`discord.service.ts:46`) · 텔레그램 `TelegramService.sendMessageAsync(chatId, …)`(`telegram.service.ts:106`). 대상은 신규 env `FEEDBACK_DISCORD_WEBHOOK_URL` · `FEEDBACK_TELEGRAM_CHAT_ID`(봇은 기존 `BOT_TOKEN_TELEGRAM`). env가 없으면 그 채널은 발송하지 않는다(safe default). 발송 실패는 작성 성공에 영향 없음(로그만, 기존 adapter의 `void` 호출 관례). 확인·상태·답변 갱신은 SQL — 조회는 `pnpm db:select`, 갱신은 담당자.
- **근거**: 관리자 역할 없음(`User.ts`). 기존 알림은 팀 단위 저장 구조라 운영자용 대상은 env로 분리한다.
- **영향**: 외부 발송 경로 신설(CLAUDE.md Ask — 사용자 승인으로 충족). 웹훅 URL은 시크릿 취급 → 스택 YAML·시크릿 반영이 **배포 직후 조치** 게이트. 알림 본문은 카테고리·제목·피드백 ID·작성자 ID + 내용 앞부분만.

## D-011 — 프론트 조사 기반 제안 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q4·Q5, 2026-10-21 — 4번은 링크 + 별도 화면) (근거: WORKLOG 2026-10-21 프론트 조사 절)
- **결정(안)**:
  1. BNB 피드백 탭은 **로그인 여부와 무관하게 항상 노출**, `/feedback` 화면 안에서 비로그인이면 기존 로그인 카드 패턴(`mypage/page.tsx:75`·`:180-212`)으로 분기. 탭을 숨기면 BNB가 세션에 의존하게 되고 로딩 중 탭 개수가 바뀌어 흔들린다. 서버는 어쨌든 401로 막는다.
  2. BNB 5탭 라벨: 375px에서 5글자 라벨(팀스페이스·마이페이지)이 넘칠 계산(실측 전) → 구현 시 Playwright로 375·320px 실측, 넘치면 라벨 단축.
  3. 내 목록 응답 `{ items, hasMore }` + `beforeId` 커서 — 채팅 "이전 더 보기"와 같은 모양. 1차는 "더 보기" 버튼.
  4. 마이페이지는 중앙 단일 카드(`mypage/page.tsx:81`)라 목록 섹션을 붙이려면 레이아웃 개편 필요 — 1차는 마이페이지에 "내 피드백" 진입 링크 + 별도 목록 화면이 변경 폭이 작다(사용자 확인 대상).
  5. 자동 메타 수정 · supersedes D-004의 `APP_VERSION`: 프론트 `package.json` 버전은 `0.1.0` 고정이라 무의미 → `BUILD_SHA`(빌드 시 `NEXT_PUBLIC_BUILD_SHA` 주입, 프론트 Dockerfile·워크플로 1줄씩, 비용 소). `USER_AGENT`는 클라이언트가 보내지 않고 **서버가 요청 헤더에서 저장**.
  6. 에러 화면(`error.tsx`) "문제 신고" → `/feedback?category=BUG` 프리필(비용 소) — 후속 후보.

## D-012 — 내 피드백 위치 · 운영자 알림 env 반영 완료 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q5 · 사용자 보고)
- **결정**: 마이페이지에는 "내 피드백" 진입 링크만 두고, 목록·상세는 별도 화면으로 만든다(마이페이지 중앙 카드 레이아웃 유지). 경로명은 프론트 구현 지시 때 정한다.
- **사실**: `FEEDBACK_DISCORD_WEBHOOK_URL`·`FEEDBACK_TELEGRAM_CHAT_ID`를 사용자가 서버·로컬에 설정 완료 — D-008의 배포 직후 조치 게이트 해소. 값은 문서에 쓰지 않는다(시크릿).

## D-013 — 스키마 세부: 컬럼명은 최신 관례 `CRTD_AT`·`MDFD_AT`, 바이트 여유 (2026-10-21)
- **상태**: ✅ 확정 (구현 세부 — D-004 컬럼명 `CREATED_DATE`·`UPDATED_DATE`·`REPLIED_DATE`를 대체)
- **결정**: `CRTD_AT`·`MDFD_AT`·`REPLIED_AT`. `PAGE_PATH`·`USER_AGENT`는 앱 500자 + `VARCHAR2(2000 BYTE)`, `TITLE` 100자 + 400바이트(한글·이모지 최대 4바이트). `USER_ID` FK는 `ON DELETE CASCADE`(본인 데이터). 인덱스 1개 `(USER_ID, FEEDBACK_ID)`.
- **근거**: 최근 테이블이 `CRTD_AT`·`MDFD_AT` — `migrations/1792396800000-CreateTeamTags.ts`, `1791960322000-CreateTeamChatMessages.ts:47`. 바이트 여유는 TEAM_TAGS `TAG_NAME` 20자/80바이트와 같은 비율.
- **버린 대안**: `CREATED_DATE`(구형 `USERS` 관례) · 24시간 카운트용 `(USER_ID, CRTD_AT)` 별도 인덱스(사용자당 행 수가 작아 불필요).

## D-014 — 구현 세부: 응답 필드·알림 경로·스로틀 값 (2026-10-21)
- **상태**: ✅ 확정 (구현 — 사용자 착수 지시 "go")
- **결정**:
  - 응답 필드 `createdAt`(= `CRTD_AT`) · 목록 `hasReply`(ADMIN_REPLY 유무, 본문 CLOB은 목록에서 읽지 않음). `userAgent`·`buildSha`는 응답 제외 — 프론트에 같은 계약 전달.
  - 운영자 알림은 Port에 `notifyFeedbackChannel(content)` 추가 — 서비스 본문에서 외부 HTTP를 직접 부르지 않는다(core.md Port/Adapter). 렌더러는 머리줄만 다르게(`renderFeedback*`) 하고 줄 구성·이스케이프는 팀 알림과 공유.
  - `sendMessageAsync`·`sendWebhookMessage`는 실패 시 throw한다 → 어댑터가 `.catch`로 로그만 남긴다.
  - 라우트 스로틀 초당 1·분당 3(`THROTTLE_FEEDBACK_*`), 24시간 상한은 DB `count`(레플리카 무관). 카운트↔저장 사이 경쟁은 초당 1 스로틀로 충분하다고 본다.
  - 인용 길이는 기존 300자(DESIGN 초안 200자 대신 공통 상수 재사용).
- **영향**: 기존 팀 알림 렌더 출력은 그대로(기존 spec 통과로 확인).
