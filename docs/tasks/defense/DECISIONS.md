## D-001 — 요구사항 원문 (2026-10-21)
- **상태**: ✅ 확정 (사용자 지시)
- **결정**:
  - 게임 모음집에 **디펜스 게임**을 추가한다. 퀄리티는 꽤 좋게.
  - **리플레이** 지원(가능하면) — 기존 게임·리플레이 코드와 테이블(`GAME_SCORES`·`GAME_REPLAYS`)을 파악해 활용한다.
  - **랭킹** 추가 — 기존 랭킹 테이블·코드 활용.
  - **레벨링(스테이지 난이도)** 을 잘 만든다.
  - 무기(타워)·몬스터에 **지상/공중** 개념, 타워에 **레벨·효과** 다양하게, **속성** 개념 등 다양하게 적용.
  - 전세계 유명 디펜스 게임을 충분히 조사해 공통 패턴을 파악하고 문서화한다(필요하면 별도 문서).
  - **구현 전에 레벨링 시스템부터 설계**하고 구현은 천천히 진행한다. 지금은 태스크 문서(SSOT) 생성까지 — 구현하지 않는다.
- **영향**: 백엔드(`games` 모듈 일반화·스키마 CHECK 확장·디펜스 엔진 사본) + 프론트(게임 카드·디펜스 화면·엔진 원본·렌더러·재생기).

## D-004 — 배속 최대 3× 허용 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q3 — 권장안)
- **결정**: 1×·2×·3×. 배속은 시뮬 밖(틱당 여러 스텝) — 리플레이에 기록하지 않는다. 서버 시간 검사는 `ticks × 1000 / (TPS × 3) ≤ 경과 + 여유`로 바꾼다(04 §4-2).
- **수용한 위험**: 오프라인으로 입력을 계산한 봇이 기다려야 하는 시간이 1/3로 준다 — 테트리스 D-015(seed 고르기 수용)와 같은 성격. 확률 요소 최소화로 완화.

## D-006 — 랭킹 단위: 1차는 무한 모드 단일 랭킹, 캠페인은 랭킹 없음 (2026-10-21)
- **상태**: ✅ 확정 (Q2 — 사용자가 의견을 물어 메인 권장안 제시 → 사용자 "권장안대로")
- **맥락**: 사용자 "무한 모드 랭킹이 나은 것 같기도 하고, 기존 랭킹 시스템과 연동성·게임 방향성도 고려해야".
- **제안**:
  - **캠페인(스테이지 1~N)** = 레벨링·학습 무대. 별점·해금만, 랭킹 등록 없음(진행은 localStorage — 영구 강화가 없어(D-005) 조작해도 랭킹 영향 0)
  - **무한 모드 1맵** = 랭킹 무대. 설계 웨이브(예: 1~30, 레벨링 공식 그대로) → 이후 무한 램프. 게임 오버로 끝난 판만 등록
  - 점수 = `도달 웨이브 × 10^6 + 마지막 웨이브 진척‰ × 10^3 + …`(04 §5-2) → 기존 `SCORE DESC, SCORE_ID ASC` 그대로
  - 2차 후보: 일일 시드 챌린지·맵별/스테이지별 보드 → 그때 `BOARD_KEY` 도입
- **근거(기존 시스템 연동)**:
  - `GAME_SCORES`는 게임당 보드 1개 + 일간·주간·전체 탭 구조(games DESIGN §3) — 무한 모드는 `GAME_TYPE='DEFENSE'` 하나로 그대로 맞는다. **`BOARD_KEY` 컬럼·인덱스 교체 마이그레이션 불필요** → 마이그레이션은 CHECK 교체만, 테트리스 장애 위험(04 R7) 제거
  - 서버 seed로 판마다 웨이브 구성이 달라 테트리스와 같은 "판마다 다른 seed → 끝날 때까지 버티기" 아케이드 구조 — 세션·검증·재생 흐름 재사용 최대
  - 스테이지 랭킹은 무누설+최적 시간으로 수렴해 상위가 대량 동점(04 R6), 보드가 스테이지 수만큼 쪼개져 이용자가 적은 서비스에선 빈 보드 다수
  - 프론트 랭킹 화면(`RankingsView`·`RankingTable`)이 보드 선택 없이 재사용 가능
- **위험**: 무한 판이 길어지면 서버 검증 CPU·세션 TTL(2시간)·리플레이 크기 증가 → 램프를 가파르게 해 상위권도 20~30분 안에 끝나도록 설계하고 판 길이 상한을 엔진 계약 상수로(D3)
- **버린 대안**: 스테이지별 랭킹(동점·보드 분산·스키마 변경), 1차부터 일일 챌린지(BOARD_KEY 선행 필요)

## D-010 — 레벨링 시스템: 압력 기준 + 목표 여유도 역산 (2026-10-21)
- **상태**: ✅ 확정 (2026-10-21 사용자 승인 — DESIGN §L 전체, §L10·§L11 포함)
- **맥락**: 사용자 "레벨링 설계 진행하고 보여줘". 리서치 02는 웨이브 예산 `B(n)=20+8n+⌊3n²/5⌋` × 톱니 배율을 제안했다.
- **결정(제안)**:
  - 난이도 기준축 = **압력(초당 유입 EHP)**. 웨이브 예산 다항식은 쓰지 않고, 웨이브 길이(`D_n`)·수입이 보조축
  - 웨이브 압력은 **목표 여유도 M(역할 톱니 × 스테이지 배율 X)** 에서 기준 봇 화력으로 역산 — 오프라인 생성기 → 사람 조정 → 정수 JSON
  - **기준 타워 곡선**(Lv1~5 누적 비용 70·120·200·340·580, 유효 DPS 14·22·34·53·84)을 §C 타워 밸런스 계약으로
  - 캠페인 8스테이지 로드맵 · 난이도 3모드(HP‰·비용‰) · 별점(KR식) · 무한 모드 설계 웨이브 30 + 정수 램프 · 점수 `웨이브×10^6 + 진척‰×10^3`
- **근거**: 모델 v1(예산 방식)에서 예산을 키워도 여유도 `M ≈ P × 간격 / 단위HP`로 예산과 무관 — 역할 톱니가 체감 난이도에 반영되지 않음. 모델 v2(역산)는 설계한 톱니가 그대로 나오고 미사용 골드 0~25%, 동시 적 최대 약 80. 무한 모드: 기준 봇 웨이브 31~33 붕괴, 상위 벽 40~45(3× 약 19~21분) (WORKLOG 레벨링 설계 절, `tools/leveling_model.py`)
- **버린 대안**: 리서치 02 예산 다항식을 1차 축으로(위 근거), 실제 플레이어 화력에 맞춰 런타임 조정(DDA — 랭킹 비교 불가, 리서치 02 §0-6)
- **영향**: §C 타워·적 수치는 기준 곡선·위협 가중치에 맞춰야 한다. 실제 수치는 시뮬레이터(§S)로 재조정

## D-011 — 반복 플레이 장치: 증강 선택 + 주간 도전 모두 1차 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 — 메인 권장은 "설계 둘 다, 구현은 증강 1차 → 주간 2차"였으나 사용자가 "둘 다 1차 구현" 선택)
- **supersedes D-006 일부**: 랭킹 단위에 **주간 도전 보드**가 1차로 추가되어 `BOARD_KEY` 컬럼이 1차에 필요하다(D-006의 "BOARD_KEY 불필요·2차 후보" 부분만 대체. 무한 모드 랭킹·캠페인 랭킹 없음은 유지)
- **맥락**: 사용자 "유저가 점점 중독적으로 꾸준히 진행할 수 있나, 아니면 수동으로 다음 단계를 계속 만들어야 하나". 메인 분석: 캠페인은 소비형(1~2시간), 무한 랭킹만으로는 판마다 전략이 같아 "중기 루프(한 판 더)"가 약함 → 수동 제작 없이 판마다 다른 경험을 만드는 시스템 필요
- **결정**:
  - **증강 선택**(무한·주간): 5웨이브마다 카드 3장 중 1장, 후보는 세션 seed로 결정, 판 안에서만 유효(D-005 영구 강화 없음과 무충돌), 선택은 명령 로그에 기록 — DESIGN §L10
  - **주간 도전**: 매주(KST 월요일) 전원 같은 seed + 맵 + 규칙 변형 2~3개, 별도 랭킹 보드 — DESIGN §L11
  - 증강·규칙 변형은 같은 **효과 엔진**(데이터 정의 효과)을 공유한다
- **근거**: 루프 3층(단기 웨이브 / 중기 한 판 / 장기 주간) 중 중기·장기가 비어 있음. 카드 20~30장·규칙 변형 15개 데이터로 조합 수천 — 이후 수동 제작 없이 지속. 리서치 01 차별화(주간 고정 시드 PvZ2 Arena·BTD6 이벤트, 로그라이트 Rogue Tower), 리서치 04 §5-4(전원 동일 seed)
- **수용한 위험**: 증강 후보가 판마다 달라 랭킹에 운 요소(테트리스 블록 순서와 같은 성격, 완화는 §L10) · `BOARD_KEY` 마이그레이션이 1차에 포함 — Entity 선배포 시 테트리스 랭킹 장애(머지 전 차단 게이트, 리서치 04 R7) · 출시 범위 증가
- **버린 대안**: 메인 권장(주간 2차) — 사용자 선택, 이용자 적은 초기 주간 보드가 비어 보일 위험은 남는다

## D-012 — 방어 체계: 물리/마법 2축 + 확장 가능한 데이터 구조 (2026-10-21)
