## D-001 — 메시지 테이블 + 멤버별 읽음 커서(watermark) 2테이블 구조 (2026-10-14)
- **상태**: ✅ 확정 (사용자: "현업 방식이고 추천하면 그렇게 진행")
- **맥락**: 카톡식 "안 읽은 인원 수", "누가 읽었는지", "안읽음 배지" 세 기능이 필요하다.
- **결정**: `TEAM_CHAT_MESSAGES`(메시지) + `TEAM_CHAT_READ_CURSORS`(팀·멤버당 1행, `LAST_READ_MESSAGE_ID`). 메시지별 읽음 행은 만들지 않는다.
- **근거**: 메시지 ID가 팀 안에서 단조 증가하므로 "어디까지 읽었나" 숫자 하나로 세 기능이 모두 계산된다(DESIGN.md §2). Slack(`last_read`)·Discord(read state `last_message_id`)가 같은 방식이다.
- **버린 대안**: 메시지×멤버 읽음 행(`message_reads`) — 행 수가 메시지 수 × 멤버 수로 늘고, 읽을 때마다 여러 행 INSERT가 필요하다.
- **영향**: 신규 Entity 2개 + 마이그레이션 2개. 기존 테이블 변경 없음. 테이블·컬럼에 `COMMENT ON` 부착(사용자 요청).

## D-002 — 영속 상태는 Oracle, Redis는 브로드캐스트·레이트 리밋만 (2026-10-14)
- **상태**: ✅ 확정 (설계 판단 — 사용자 요청 "Redis·DB 현업 수준으로 적절히")
- **결정**: 메시지·읽음 커서의 원본(SoT)은 Oracle. Redis는 ① 기존 Socket.IO 멀티 레플리카 전파 ② 채팅 이벤트 레이트 리밋에만 쓴다. 안읽음 수 캐시는 두지 않는다.
- **근거**: 운영 Redis는 `maxmemory 128mb` + `allkeys-lru`(README "로컬 Redis 실행") — 메모리가 차면 아무 키나 지우므로 유실되면 안 되는 상태를 둘 수 없다. 안읽음 수 조회는 `(TEAM_ID, MESSAGE_ID)` 인덱스 범위 스캔이라 캐시 없이도 싸다(WORKLOG 부하 추정).
- **버린 대안**: Redis 카운터(`HINCRBY`) + DB write-behind — 축출 시 카운트가 틀어지고 복구 로직이 필요하다. 이 트래픽에선 복잡도만 는다.

## D-003 — 메시지 ID는 IDENTITY (ORDER), 커서는 증가만 (2026-10-14)
- **상태**: ✅ 확정 (설계 판단)
- **결정**: `MESSAGE_ID NUMBER GENERATED ALWAYS AS IDENTITY (ORDER)`. 커서 UPDATE는 `WHERE LAST_READ_MESSAGE_ID < :id` 조건부라 뒤로 가지 않는다.
- **근거**: Autonomous DB는 RAC 기반이라 기본(NOORDER) 시퀀스는 인스턴스 간 발급 순서가 보장되지 않는다. 커서 모델은 "ID 순서 = 시간 순서"에 의존한다. ORDER 비용은 이 트래픽에서 무시할 수준이다.
- **알려진 한계**: ID 발급 순서와 커밋 순서가 수 ms 어긋나면 늦게 커밋된 작은 ID 메시지가 "읽음"으로 계산될 수 있다. 단건 INSERT 트랜잭션이라 창이 매우 짧아 수용한다.

## D-004 — 신규 멤버도 이전 대화를 본다, 안읽음 기준점은 가입 시점 (2026-10-14)

## D-005 — 메시지 길이: 글자 수 + 바이트 이중 제한, 컬럼 VARCHAR2(4000 BYTE) (2026-10-14)
- **상태**: ⛔ D-013으로 대체 (2026-10-14 사용자 B안 선택)
- **맥락**: 현재 200자 제한(백엔드 `team.gateway.dto.ts` `@MaxLength(200)`, 프론트 `TeamChatPanel.tsx` `maxLength={200}`).
- **결정**: `@MaxLength(N)` + `@IsByteLength(1, 4000)`. 컬럼 `VARCHAR2(4000 BYTE)`.
- **근거**: VARCHAR2는 가변 길이 — 짧은 메시지는 실제 바이트만 차지하므로 한도를 늘려도 용량이 늘지 않는다. class-validator는 이모지 변형 선택자(U+FE0F)를 0자로 세서 "❤️"가 1자 = 6바이트가 된다 → 글자 수만 보면 ORA-12899가 날 수 있다. 한글 1자 = 3바이트라 1000자 = 3000바이트로 4000 안에 들어간다. CLOB은 인덱스·성능 이점이 없어 쓰지 않는다.

## D-013 — 메시지 길이 4,000자 + CONTENT를 CLOB으로 (D-005 대체 제안) (2026-10-14)
- **상태**: ✅ 확정 — B안 (2026-10-14 사용자: "B안으로 진행")
- **맥락**: `VARCHAR2`는 표준 설정에서 최대 4000바이트다. 한글은 1자 3바이트라 VARCHAR2로는 약 1,300자가 한계다.
- **선택지**:
  | 안 | 한도 | 컬럼 | 비고 |
  |---|---|---|---|
  | A | 1,300자 | `VARCHAR2(4000 BYTE)` (현재 초안) | 가장 단순 |
  | **B (권장)** | **4,000자** | **`CLOB`** | `TASK_COMMENTS.COMMENT_CONTENT`가 이미 CLOB(선례). Telegram 4,096자·Discord 유료 4,000자와 같은 수준 |
  | C | 10,000자 이상 | `CLOB` | 화면에서 긴 메시지 접기 UI가 필수, 도배 1건의 크기가 커짐 |
- **용량**: CLOB도 약 4000바이트 이하는 행 안에 저장돼(기본 `ENABLE STORAGE IN ROW`) 짧은 메시지는 VARCHAR2와 같은 만큼만 차지한다. 그보다 긴 메시지만 별도 LOB 영역에 최소 1블록(약 8KB) 단위로 저장된다. 긴 메시지는 드물어 총량 영향은 미미하다.
- **확정 시 영향**: 마이그레이션 `CONTENT` 컬럼 타입 변경(⚠️ 실행 전이어야 함), Entity `type: 'clob'`, `@MaxLength(4000)` + `@IsByteLength(1, 16000)`(바이트 상한은 페이로드 크기 방어용), 프론트 `maxLength`. TypeORM Oracle 드라이버는 CLOB을 문자열로 받는다(`OracleDriver.js` `fetchAsString = [DB_TYPE_CLOB]`).

## D-014 — Redis 증설 불필요, 채팅 데이터는 Redis에 저장하지 않는다 (2026-10-14)
- **상태**: ✅ 확정 (D-002 재확인 — 사용자 질문 "채팅도 Redis에 가나?")
- **결정**: 메시지는 전송 즉시 Oracle에 저장한다(캐시·지연 쓰기 없음). Redis에는 채팅 내용이 남지 않는다 — Pub/Sub은 저장 없이 통과하는 파이프다. 128MB 유지.
- **근거**: Redis에 상주하는 채팅 관련 데이터는 레이트 리밋 카운터(10초 TTL)뿐이다. 동시 접속 1,000명 기준으로도 온라인 상태 + 카운터가 1MB 미만(WORKLOG 2026-10-14 용량 한도 절).
- **재검토 조건**: Redis `used_memory`가 64MB(50%)를 넘거나, read-state·안읽음 조회 지연이 실측으로 문제가 될 때 cache-aside 캐시를 검토한다.

## D-020 — 메시지는 전송 즉시 DB에 직접 저장, Redis 버퍼 후 일괄 반영(write-behind)은 쓰지 않는다 (2026-10-14)
- **상태**: ✅ 확정 (사용자 질문 "Redis에 모았다가 주기적으로 DB에 반영하는 게 정석 아닌가?"에 대한 분석. D-002·D-014 재확인)
- **결정**: 현행 설계 유지. 메시지는 DB COMMIT이 끝난 뒤 방에 뿌린다("저장 후 전달").
- **근거** (상세는 WORKLOG 2026-10-14 write-behind 분석 절):
  - write-behind는 Redis에서 아직 DB로 넘어가지 않은 메시지가 Redis 장애·재시작·키 축출 때 사라진다. 운영 Redis는 `allkeys-lru` 128MB라 이 위험이 실제로 있다
  - 읽음 커서는 DB의 `MESSAGE_ID` 순서에 의존한다. 버퍼를 두면 ID를 Redis에서 따로 발급해야 하고 원본이 둘이 된다
  - 이력 조회 때 Redis와 DB를 합쳐야 하고, flush 작업에 단일 실행 가드·재시도·중복 처리가 필요하다
  - 얻는 것은 DB 왕복 감소뿐인데, 예상 쓰기 부하는 DB 처리량의 1% 미만이다
- **재검토 조건과 순서**: 실측에서 DB가 병목이면 ① 멤버십 확인 짧은 TTL 캐시, 읽음 debounce 늘리기 → ② 커넥션 풀 증설 → ③ 그래도 부족하면 Redis Streams·Kafka 같은 디스크에 기록되는 큐 + 컨슈머. LRU 캐시를 버퍼로 쓰는 방식은 고려하지 않는다.

## D-024 — 재연결·탭 복귀 시 최신 페이지로 목록 통째 교체 (빈 구간 채우기 폐기) (2026-10-14)
- **상태**: ✅ 확정 (2026-10-14 사용자: "1번대로 진행")
- **맥락**: 프론트 리뷰가 3라운드 상한에서 수렴하지 않았다(5→6→2건). 결함은 모두 `afterId` 빈 구간 채우기 장부(gap 시작점, room 참가 세대, 미확인 전송 추적)의 경계 조건이었다. 실시간 수신과 끼워 넣기가 동시에 일어나는 구조라, 고칠 때마다 장부가 복잡해지고 새 틈이 생겼다(WORKLOG 리뷰 1~3라운드 절).
- **결정**: room에 다시 참가하거나 탭이 다시 보이면, 이력을 열어 둔 상태일 때 최신 페이지(50개)를 다시 조회해 서버 메시지 목록을 통째로 교체한다. 전송 중(`serverId` 없음)인 내 메시지만 유지하고, 교체가 끝날 때까지 읽음 전송을 보류한다. read-state도 같은 시점에 다시 조회한다.
- **근거**: 업계 정석은 "짧은 끊김은 서버가 순번으로 재전송, 실패하거나 오래 끊기면 전체를 다시 받기"의 2단계다(Discord RESUME/재연결, Telegram `getDifference`). 우리는 서버에 이벤트 순번 장부가 없어서 1단계를 클라이언트가 추측으로 하고 있었다. 정석의 2단계(전체 재수신)만 쓰는 편이 이 규모에서 정확하고 단순하다.
- **대가**: 재연결 직후 위로 스크롤해 보던 위치가 초기화된다. 더 오래된 메시지는 다시 위로 스크롤하면 `beforeId`로 불러온다.
- **버린 대안**: 리뷰 반복(수렴 시점 예측 불가), 현 상태로 실측(타이밍 의존 결함은 수동 테스트로 잘 안 잡힘)
- **나중의 1단계**: Socket.IO connection state recovery(4.6+)는 현재 Redis 어댑터에서 지원되지 않고 Redis Streams 어댑터가 필요하다. 끊김으로 인한 사용자 불편이 실제로 관찰되면 검토한다.
- **영향**: 백엔드 계약 변경 없음. `afterId`는 계약에 그대로 둔다(쓰지 않아도 무해).

## D-025 — 보낸 사람 기준 메시지 순서는 프론트 전송 대기열로 보장 (한 소켓당 전송 1건만 진행) (2026-10-15)
- **상태**: ✅ 확정 (실측에서 발견한 결함의 해결 방식, 설계 판단)
- **맥락**: 실측에서 한 사람이 빠르게 연속 전송하자 저장 ID 순서가 보낸 순서와 달라졌다(WORKLOG 실측 절: `6:1 7:2 8:6 9:3 …`). 모든 화면이 같은 순서로 보이지만, 보낸 사람이 친 순서와 다르다.
- **원인**: Socket.IO는 같은 소켓의 이벤트를 기다리지 않고 동시에 처리한다. 게다가 `WsJwtGuard`가 이벤트마다 DB로 사용자를 조회하는데(`ws-jwt-auth.guard.ts` `canActivate`), 이 가드가 핸들러보다 먼저 실행된다. 그래서 핸들러에 도착하는 순서부터 이미 섞인다.
- **결정**: 프론트가 소켓당 전송을 1건씩만 진행한다(outbox). 앞 메시지의 `chatReceived`(같은 clientMsgId echo)나 `error`(같은 clientMsgId)를 받거나, 일정 시간이 지나 실패로 판정되면 다음 메시지를 보낸다. 백엔드 계약은 바꾸지 않는다.
- **버린 대안**:
  - 핸들러 안의 소켓별 큐: 실제로 구현해 실측했지만, 가드 단계에서 이미 순서가 바뀌어 보장되지 않았다(`… 8 10 9`). 되돌렸다
  - 가드의 사용자 조회를 연결 시 1회로 캐시: 모든 WS 이벤트에 영향이 가는 인증 변경이고, 연결 중 비활성화된 사용자를 놓친다. 범위 밖
- **알려진 한계**: 서로 다른 탭(다른 소켓)이 동시에 보낸 메시지끼리는 서버 도착 순서를 따른다(카톡·슬랙과 같음).
