## D-004 — 낚시 소켓 상한·빈도 값 (2026-11-16)
- **맥락**: A2 — 낚시 이벤트는 같은 맵 전원에게 중계되는데 서버 빈도 제한·입력 상한이 없다(실시간#3)
- **결정**: 프론트 정상 최대값에 여유를 둔다. 입력: fishName ≤20자, size ≤1000, weight ≤100000, pointId ≤32자, mapId ≤64자. 빈도(소켓 단위 고정 윈도, 초과분은 조용히 버림): move 40/1초, state 10/1초, chat 10/10초, catch 5/10초. 소켓 메시지 1건 상한 100KB(Socket.IO 기본 1MB)

- **버린 대안**: Redis INCR 카운터(GameRoomRateLimiter) — 이동이 초당 수십 건이라 이벤트마다 Redis 왕복이 붙는다. 소켓은 한 레플리카에 붙어 있으니 소켓 데이터의 윈도로 충분하다(공유 상태 아님)
- **영향**: `fishing-rate-limit.ts`(신규), `fishing.gateway.ts`, `fishing.gateway.dto.ts`, `fishing-ws.guard.ts`(소켓 타입), `redis-io.adapter.ts`

## D-005 — 포트리스 남은 끊김 기록 해제를 submit 안으로 옮긴다 (2026-11-16)
- **맥락**: A6 — turnSubmit이 `clearStaleDisconnect`(setDisconnected = 경기 전체 load) → `submit`(load) 순으로 경기 JSON(지형 2048열 + 누적 행동)을 두 번 읽는다. 끊김 기록이 없는 평상시에도 읽기가 한 번 더 붙는다
- **결정**: `submit`이 읽은 경기에서 제출자 자리에 끊김 기록이 있을 때만 같은 버전으로 CAS 해제 후 다시 읽는다(판정 전 — 거부되는 제출이어도 해제). resync는 기존 `clearStaleDisconnect`를 유지한다. 깨우기 타이머는 경기마다 마지막 예약만 `processDue`를 부른다(로컬 번호, 끝난 경기는 무효)
- **근거**: `fortress-room.service.ts` turnSubmit · `fortress-match.service.ts` setDisconnected·submit. 테스트 "끊김 기록이 없으면 제출 1건에 경기를 한 번만 읽는다", "거부되는 제출이어도 … 지운다", 기존 R1-1 유지
- **버린 대안**: 방 기록의 끊김 여부로 빠른 경로 — 남은 기록은 방·경기 기록이 어긋난 경우라 방 기록으로는 판단할 수 없다. 경기 JSON에서 지형 분리 — 저장 모양이 바뀌어 L 난이도(C 등급 유지)
- **영향**: 제출 경로 Redis 읽기 2회 → 1회. 깨우기 타이머는 여전히 쌓이지만 앞선 것은 Redis를 읽지 않는다
