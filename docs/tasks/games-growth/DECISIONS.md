# 게임 유입·바이럴 — 결정 로그

> 현황은 [STATUS.md](STATUS.md). append-only — 뒤집힌 결정은 새 항목에 `supersedes D-00N`.

## D-001 SEO 1차 범위 — 기본기부터, 프론트 단독

- **요청(2026-10-24)**: 디펜스·테트리스 등 게임에 SEO 작업이 안 돼 있으면 진행해서 트래픽을 가져오고 싶다.
- **결정**: 메타·canonical, robots·sitemap, JSON-LD(VideoGame/WebApplication·ItemList·WebSite), 게임 페이지 SSR 소개 텍스트, 리플레이 페이지 제목 개선. 먼저 감사하고 빠진 것만 채운다.
- **이유**: 게임 페이지는 캔버스 위주라 검색엔진이 읽을 텍스트가 거의 없다(감사로 확인 예정). 색인 가능한 텍스트와 사이트맵이 없으면 다른 최적화의 효과가 없다.
- 리플레이 페이지는 전부 색인하지 않는다. 내용이 얇은 페이지가 대량으로 생기면 사이트 품질 평가에 불리할 수 있어서, 인기·상위 기록 일부만 sitemap에 넣는다.
- 도메인은 env로만 다룬다(공개 저장소 — CLAUDE.md Never).

## D-002 유입 백로그 우선순위 기준

- 기준: (1) 재방문 루프를 만드는가 (2) 공유물이 저장소 밖으로 퍼지는가 (3) 이미 있는 자산을 재사용하는가(규모 대비 효과).
- B1 데일리 시드가 1순위다. 매일 돌아올 이유와 공유물(결과 텍스트)을 한 번에 만들고, 디펜스 주간 보드의 "전원 같은 시드" 구조를 그대로 쓸 수 있다.
- B3(등록 직후 공유 유도)은 규모가 가장 작아서 B1과 함께 해도 된다.
- 외부 알림(B6)은 실제 사용자에게 발송되므로 착수 전 사용자 승인이 필요하다(CLAUDE.md Ask).

## D-003 착수 범위 — B1·B2·B3·B5, B4는 설명 후 보류

- **요청(2026-10-24)**: B6·B7·B8을 뺀 전부를 해 보고 싶다. B4는 무엇인지 설명을 먼저 듣겠다.
- **결정**: B1·B2·B3·B5에 착수한다. B4(하이라이트 클립)는 설명만 하고, 사용자 결정 전까지 보류한다.
- 순서: B1(백엔드 먼저) → B3(프론트만) → B2 → B5. 프론트 세션은 조회수 → SEO(G1) → 위 순서로 받는다.

## D-004 B1 오늘의 테트리스 — 디펜스 주간 보드 구조를 일 단위로

- 보드 키는 `daily-YYYY-MM-DD`(KST 날짜)다. seed는 `HMAC(GAME_WEEKLY_SEED_SECRET, "tetris-daily:{boardKey}")`라 전원이 같은 판을 받는다. 비밀값을 섞으므로 내일 seed를 미리 계산할 수 없다.
- 세션 발급은 `POST /games/tetris/sessions { board: 'daily' }`(디펜스 `weekly`와 같은 방식)다. 기존 테트리스 기본 보드 `default`는 그대로 둔다.
- 리플레이 공개는 그날이 끝나고 세션 유효 시간(2시간)이 지난 뒤다. 진행 중에 남의 입력을 그대로 복제하지 못하게 하려는 것으로, 디펜스 D-011과 같은 이유다.
- 하루 1판 제한(Wordle식)은 **서버에서 강제하지 않는다**. 비로그인이라 신원으로 막을 수 없기 때문이다. 같은 리플레이 반복 등록은 기존 REPLAY_HASH 유니크가 막는다. "오늘 첫 판만 공유 카드" 같은 연출은 프론트 localStorage로 한다.
- 비밀값이 없으면 데일리만 503이다(디펜스 주간과 같은 GAME_WEEKLY_UNAVAILABLE 경로). 다른 보드는 정상 동작한다.
- 결과 공유 텍스트(이모지 요약 + 링크)는 프론트가 만든다.

## D-005 B2 도전장 — 기록별 도전 보드, 메인 랭킹과 분리

- 기본값(사용자 이견 시 갱신): 도전장 링크로 들어오면 그 기록과 **같은 seed**로 플레이한다. 결과는 기록별 도전 보드 `challenge-{scoreId}`에 등록하고, 메인 랭킹(`default`·데일리)에는 넣지 않는다.
- 이유: 공개 리플레이로 seed를 알 수 있어 미리 연습할 수 있다. 공정성이 다르므로 메인 랭킹과 섞지 않는다. 대신 "이 도전장 순위"가 생겨 친구끼리 경쟁 화면이 된다.
- 대상은 재생을 공개한 기록만이다. 진행 중 데일리·주간 기록은 도전장을 만들 수 없다(같은 판 복제와 같은 문제).

## D-006 B3 자랑 유도 — 프론트만

- 등록 응답에 이미 있는 기간별 순위(ranks.daily·weekly·all)와 개인 최고 갱신 여부(프론트 저장 값)로, 상위권 진입·최고 갱신일 때만 공유 버튼을 강조하고 문구를 바꾼다. 백엔드 변경은 없다.

## D-007 B5 명예의 전당·배지 — 계산형, 배지는 로그인 기록만

- 기본값(사용자 이견 시 갱신): 지난 일간·주간·데일리 보드의 1~3위를 GAME_SCORES에서 **조회 시점에 계산**한다. 기록이 불변이라 스냅샷 테이블과 스케줄러가 필요 없다(숨김 처리는 즉시 반영된다).
- 이름 옆 배지는 **로그인 사용자(USER_ID) 기록만** 붙인다. 비로그인 이름은 누구나 같은 이름을 쓸 수 있어, 이름 기준 배지는 사칭이 가능하기 때문이다. 명예의 전당 목록 자체는 기록 단위라 비로그인 기록도 보인다.

## D-008 B4 보류 확정 · 나머지 착수

- **요청(2026-10-24)**: B4 하이라이트 클립은 미루고, 나머지(B1·B2·B3·B5)는 전부 진행한다.
- D-005·D-007의 기본값(도전장은 메인 랭킹과 분리, 배지는 로그인 기록만)은 이견이 없어 확정한다.

## D-009 B2 세부 — 순위 보드와 규칙 보드 분리, 원본 복제 차단

- 디펜스 검증은 보드 키로 모드·주간 맵 변형을 정한다(`defense-verify.ts` `defenseModeOf`). 그래서 도전장 세션은 **순위 보드 `challenge-{scoreId}`와 규칙 보드(원본 기록의 보드 키)를 따로** 갖는다. 검증은 규칙 보드로 하고, 저장은 순위 보드로 한다. 테트리스·디펜스 공통이다.
- 원본 기록의 엔진 버전이 현재와 다르면 같은 seed라도 다른 판이 되므로 도전장을 열지 않는다(409).
- 원본 리플레이(공개)의 입력을 그대로 내면 원본과 같은 점수가 된다. 그래서 원본 replayHash와 같은 리플레이는 거부한다. 원본 해시는 원본 보드 키 기준으로 계산한다.

## D-010 B5 세부 — 엔진이 기간 목록, 서비스가 기간별 1~3위, Redis 캐시

- 엔진이 "끝났고 재생이 공개된" 기간 목록을 낸다(`hallOfFamePeriods`).
  - 테트리스: 기본 보드의 지난 주 8개(등록 시각 범위) + 데일리 보드 지난 7일
  - 디펜스: 주간 보드 지난 8주
- 서비스가 기간마다 1~3위를 조회한다. 기록 단위라 비로그인도 보이고, IP·USER_ID는 응답에 싣지 않는다.
- 결과는 Redis에 10분 캐시한다. 랭킹 목록의 배지 계산이 매 요청마다 기간 수만큼 쿼리하지 않게 하려는 것이다. Redis를 못 쓰면 매번 계산한다.
- 배지는 랭킹 항목의 `trophies: { gold, silver, bronze }`다. 로그인 기록이고 그 사용자가 캐시 창 안에서 입상한 경우에만 붙고, 그 외는 null이다.

## D-011 리플레이는 noindex 유지, sitemap 제외 (supersedes D-001의 리플레이 sitemap 항목)

- 프론트 감사 결과: 리플레이 페이지는 이미 `robots: { index: false }`다(`replayMetadata.ts`). SSR HTML은 재생기 로딩 상태뿐이라 내용이 얇다.
- noindex 페이지를 sitemap에 넣으면 Search Console이 오류로 표시하므로 리플레이는 sitemap에서 뺀다. 제목 개선과 공유 미리보기 카드는 적용한다.
- 리플레이를 색인시키려면 기록 정보 텍스트를 SSR로 내야 한다. 그때 다시 결정한다.

## D-012 B2는 테트리스만 — 디펜스 도전장은 후속

- 디펜스 기록은 보드 키가 곧 규칙이다. 도전장 기록을 `challenge-{id}` 보드로 저장하면 재검증할 때와 프론트가 재생할 때 규칙 보드를 알 수 없다.
- 지원하려면 규칙 보드를 저장할 곳(컬럼 또는 detail)이 필요하므로, 스키마 결정과 함께 후속으로 미룬다. 엔진 항목 `supportsChallenge`로 게임마다 켜고 끈다(디펜스는 422).
- B5 배지 노출 범위: 랭킹·인기 목록·기록 요약·재생 응답의 항목에 `trophies`를 싣는다. 사용자 ID는 배지 계산에만 쓰고 응답에 싣지 않는다.

## D-013 백엔드 리뷰 1라운드 반영 (review-flow·Opus, 2026-10-24)

- **도전장 복제 차단 범위 확대** (supersedes D-009의 "원본 replayHash와 같은 리플레이"): 데일리 보드는 그날 기록이 모두 같은 seed다. 그래서 공개된 그날 1위 입력으로 하위 기록의 도전장을 이길 수 있었다. 이제 **원본 보드 기준 해시가 GAME_SCORES에 이미 있으면** 거부한다(원본 1건 → 보드 전체). 남는 구멍: 같은 원본 보드를 둔 다른 도전 보드(`challenge-R2`)의 기록 복사는 보드 키가 달라 해시가 다르다. seed 단위 해시가 필요해 스키마 결정 사항이므로 후속으로 둔다.
- **명예의 전당 계산 1회** (D-010 보완): 화면 조회가 시상대를 두 번 계산하던 것을 한 번으로 줄였다. 캐시가 빈 순간의 같은 레플리카 동시 요청은 진행 중 계산을 공유한다(결과를 메모리에 두지 않고 중복 쿼리만 막는다). Redis를 못 쓰면 랭킹 항목의 배지는 건너뛴다(`trophies` null). 화면 조회는 매번 계산한다.
- 조회 집계 저장 직전에 기록이 지워져 FK 위반(ORA-02291)이 나면 500 대신 404를 준다. Redis MULTI의 명령 에러는 결과 tuple로 오므로 확인해서 fail-open으로 처리한다.
- **문서 정정**:
  - D-004의 "GAME_WEEKLY_UNAVAILABLE 경로"는 실제로는 새 코드 `GAME_DAILY_UNAVAILABLE`(503)이다.
  - D-007의 "숨김 처리는 즉시 반영"은 "다음 캐시 갱신(최대 10분)에 반영"이다.
  - README에 `GAME_IP_HASH_SECRET`이 없으면 조회수·시청시간의 IP 상한도 꺼진다고 적었다.
