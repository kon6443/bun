## D-001 — 요구사항 원문 (2026-10-19)
- **상태**: ✅ 확정 (사용자 지시)
- **결정**:
  - 태그는 **팀 단위**로 관리한다. 팀 생성 시 태그는 0개.
  - 팀의 **활성 멤버 누구나** 태그를 생성·수정·삭제할 수 있다 (리더 전용 아님).
  - 태그는 이름 + **색상**을 저장한다. 색상은 컬러 휠(원형 전체 색상) + 스포이드 + 추천 색 5개 정도.
  - 한 태스크에 태그 **여러 개**를 붙일 수 있다. 태스크 카드에 태그를 표시한다.
  - 입구 3곳 — `/teams/:teamId` 페이지, 태스크 생성, 태스크 수정. **공통 모달 컴포넌트 하나**로 간단하게.
  - UX는 노션 태그(multi-select 속성)와 비슷한 느낌.
- **영향**: 백엔드(스키마·REST·소켓) + 프론트(모달·폼·카드). 세션 구성은 D-002.

## D-002 — 세션 구성: 메인 bun-f5가 백엔드·문서·프론트 지시를 모두 관리 (2026-10-19)
- **상태**: ✅ 확정 (사용자 지시)
- **결정**: 사용자는 메인(`bun-f5`)과만 소통한다. 백엔드 작업은 메인이, 프론트 작업은 `next-bun-6c`가 한다 — 사용자는 백/프를 구분해 말하지 않으므로 메인이 라우팅한다. 이 폴더는 메인만 수정하고, 프론트 세션은 보고·질문을 메인에 보낸다.

## D-003 — 스키마: 태그 정의 테이블 + 태스크-태그 연결 테이블 (2026-10-19)
- **상태**: ✅ 확정 (D-019) — 구체화는 D-012·D-014·D-018
- **맥락**: 팀별 태그 목록과 태스크당 N개 태그(N:M)가 필요하다.
- **결정**:
  - `TEAM_TAGS` — `TAG_ID`(IDENTITY PK), `TEAM_ID`(FK → TEAMS, ON DELETE CASCADE), `TAG_NAME`, `TAG_COLOR`(`#RRGGBB` 7자, 대문자 정규화), `CRTD_AT`·`CRTD_BY`·`MDFD_AT`. 유니크 `(TEAM_ID, TAG_NAME)`.
  - `TEAM_TASK_TAGS` — `TASK_ID`(FK → TEAM_TASKS, CASCADE), `TAG_ID`(FK → TEAM_TAGS, CASCADE), `CRTD_AT`. PK `(TASK_ID, TAG_ID)`, 인덱스 `(TAG_ID)`.
  - 마이그레이션 2파일(1파일 1목적), 멱등 가드·`COMMENT ON`·`down()` — `CreateTeamChatReadCursors` 형식을 따른다.
- **근거**: 태그는 팀 소속이고 태스크와 N:M이다. 태스크 테이블에 문자열(콤마 구분)로 넣으면 이름 변경·삭제가 모든 태스크를 고쳐야 하고 필터·집계가 불가능하다.
- **버린 대안**: ① `TEAM_TASKS.TAG_IDS` 문자열/JSON 컬럼 — 참조 무결성 없음, 태그 삭제 시 전수 갱신. ② 전역(팀 무관) 태그 — 요구사항(D-001 팀 단위)과 불일치.
- **영향**: 신규 Entity 2개 + 마이그레이션 2개. 기존 테이블 변경 없음 → 앱보다 먼저 적용해도 기존 기능 무영향.

## D-004 — 태그 삭제는 하드 삭제, 연결은 CASCADE로 함께 제거 (2026-10-19)
- **상태**: ✅ 확정 (D-019, 사용자: 완전삭제 + 확인창)
- **결정**: `DELETE /tags/:tagId`는 행을 지우고, 붙어 있던 태스크에서도 즉시 사라진다(FK CASCADE). 프론트는 삭제 전 확인창에 "N개 태스크에서 제거됩니다"를 보여준다(사용 수는 목록 응답의 `taskCount`).
- **근거**: 노션도 옵션 삭제 시 모든 페이지에서 제거한다. 소프트 삭제는 "삭제된 태그가 태스크에 남아 보이는가"라는 별도 정책과 복원 UI가 필요해 단순함 요구(D-001)에 어긋난다.
- **버린 대안**: STATUS 컬럼 소프트 삭제 — 같은 이름 재생성 시 유니크 충돌 처리까지 필요해진다.

## D-005 — REST 계약 (2026-10-19)
- **상태**: ✅ 확정 (D-019) — 재정렬 API는 D-017
- **결정**:
  - `GET    /teams/:teamId/tags` → `[{ tagId, tagName, tagColor, taskCount }]` (이름순 또는 생성순 — Q5)
  - `POST   /teams/:teamId/tags` `{ tagName, tagColor }` → 201 태그
  - `PATCH  /teams/:teamId/tags/:tagId` `{ tagName?, tagColor? }` → 200 태그
  - `DELETE /teams/:teamId/tags/:tagId` → 200
  - 태스크 생성·수정 바디에 `tagIds?: number[]` — 수정에서 `undefined`는 변경 없음, 배열은 **전체 교체**(`[]`는 모두 제거). 생성·수정은 태스크 저장과 연결 교체를 한 트랜잭션으로.
  - 태스크 목록·상세 응답의 각 태스크에 `tags: [{ tagId, tagName, tagColor }]` 추가 (**API 계약 추가** — 기존 필드 변경 없음, 구 프론트는 무시).
  - 권한: 모든 태그 API는 `verifyTeamMemberAccess`(활성 팀·활성 멤버) — 기존 태스크 API와 동일.
- **에러(도메인 에러 DTO로 정의)**: 이름 중복 409 · 태그 없음/다른 팀 태그 404 · `tagIds`에 다른 팀·없는 태그 포함 400 · 한도 초과 400(Q2) · 형식 위반은 ValidationPipe 400.
- **근거**: 태그 연결을 태스크 생성·수정 바디에 싣으면 폼 저장 1회로 끝난다(노션처럼 별도 "붙이기" API를 두면 폼 저장과 태그 저장이 따로 실패할 수 있다). 목록 조회는 태스크 쿼리에 조인하면 행이 태그 수만큼 불어나므로, 태스크 ID 목록으로 **연결을 한 번 더 조회해 서비스에서 붙인다**(N+1 아님, 쿼리 1회 추가).
- **영향**: `getTeamTasksBy`는 알림 경로도 쓰므로 건드리지 않고, 응답 경로(`getTasksByTeamId`·`getTaskWithComments`·생성·수정 반환)에서만 `tags`를 붙인다.

## D-006 — 실시간: 태그 이벤트 3종 + 태스크 이벤트에 `tags` 포함 (2026-10-19)
- **상태**: ✅ 확정 (D-019) — `tagsReordered`는 D-017
- **결정**: room `team-{teamId}`에 `tagCreated`·`tagUpdated`(태그 전체) · `tagDeleted`(`tagId`) 발행. `taskCreated`·`taskUpdated` 페이로드에 `tags` 추가. 프론트는 태그 이벤트로 팀 태그 목록과 카드의 칩(이름·색)을 갱신한다.

## D-007 — 색상: `#RRGGBB` 저장, 글자색은 프론트가 대비로 자동 결정 (2026-10-19)
- **상태**: ✅ 확정 (D-019)
- **결정**: 서버는 `^#[0-9A-Fa-f]{6}$`만 검증하고 대문자로 정규화해 저장한다. 알파(투명도)는 받지 않는다. 칩 글자색(검정/흰색)은 프론트가 휘도로 계산한다 — 서버에 저장하지 않는다.
- **근거**: 노션은 고정 10색 팔레트지만 사용자는 자유 색상(휠·스포이드)을 원한다. 자유 색은 배경-글자 대비를 사용자가 보장할 수 없으므로 표시 시점에 계산한다.

## D-010 — 컬러 피커: 추천 5색 + 원형 휠 + HEX 입력, 스포이드는 기능 감지 (2026-10-19)
- **상태**: ⛔ 피커 부분은 D-013(react-colorful)으로 대체 · 추천 5색·HEX 입력·스포이드 기능 감지는 유효
- **결정**: 추천 5색(다크 배경 기준 red/amber/emerald/sky/violet 400 계열) 원형 버튼 + 원형 휠(conic-gradient 색상 + radial 채도, 명도 슬라이더) + HEX 입력 필드. 스포이드(`EyeDropper` API)는 `'EyeDropper' in window`일 때만 버튼 노출.
- **근거**: 프론트에 색상 라이브러리가 없다. `react-colorful`(≈2.8KB, 무의존)은 사각 피커라 "원형 휠" 요구와 다르고 신규 의존성은 승인 사항. 직접 구현은 150~250줄(터치·키보드 포함 약 1일). `EyeDropper`는 Chromium 데스크톱 전용 — **Safari·Firefox·모바일 전부 미지원**이라 모바일 우선 앱의 대다수 사용자에겐 스포이드가 보이지 않는다.
- **버린 대안**: `<input type="color">` — iOS 네이티브 피커는 UI 통제 불가, iOS 폭 이슈.

## D-011 — 칩 표시 범위와 스타일 (2026-10-19)

## D-012 — 정렬·중복·기본 색 (2026-10-19)
- **상태**: ✅ 확정 (D-019) — 정렬 부분은 D-017로 대체
- **결정**: 태그 목록·칩 순서는 **생성순**(`TAG_ID` 오름차순). 이름 중복은 팀 안에서 **대소문자·앞뒤 공백 무시**로 판정(앞뒤 공백은 저장 전 trim, 비교는 `UPPER(TAG_NAME)` 함수 기반 유니크 인덱스). 새 태그 기본 색은 추천 5색을 순환.
- **근거**: 드래그 재정렬이 비목표라 별도 정렬 컬럼이 필요 없다. 앱 레벨 중복 검사만으로는 동시 생성 경쟁을 못 막으므로 DB 유니크가 최종 방어선(위반 시 409).
- **영향**: D-003의 유니크 `(TEAM_ID, TAG_NAME)`을 `(TEAM_ID, UPPER(TAG_NAME))` 함수 기반 인덱스로 구체화.

## D-013 — 컬러 피커는 `react-colorful` (supersedes D-010의 "원형 휠 직접 구현") (2026-10-19)
- **상태**: ✅ 확정 (사용자 Q1: "react-colorful … 간단하고 좋을 거 같은데. 사파리·파폭·모바일 다 지원하면 이거로")
- **결정**: 프론트에 `react-colorful` 추가(신규 의존성 — 사용자 승인). 구성: 추천 5색 원형 버튼 + `HexColorPicker`(사각 채도 판 + 색상 바) + `HexColorInput`. 스포이드는 D-010대로 `'EyeDropper' in window`일 때만 노출.
- **브라우저 지원**: react-colorful은 순수 React + DOM 포인터/터치 이벤트라 Safari·Firefox·모바일(iOS/Android)에서 동작하고, 터치·키보드 조작을 지원한다(라이브러리 README 표기 — 메인이 이번 세션에서 네트워크로 재확인하지 못함). **스포이드는 react-colorful 기능이 아니라 브라우저 `EyeDropper` API**라 라이브러리와 무관하게 Chromium 데스크톱에서만 보인다.
- **설치 시 확인(프론트)**: 최신 버전·무의존성·React 19 peer 경고 여부를 `pnpm add` 결과로 확인해 WORKLOG에 기록. 경고가 있으면 메인에 보고.
- **버린 대안**: 원형 휠 직접 구현 — 약 1일 + 접근성 직접 구현. 사용자가 단순함을 택함.

- **상태**: ✅ 확정 (사용자 Q2)

## D-015 — 태그 필터를 이번 범위에 포함, 클라이언트 필터 (2026-10-19)
- **상태**: ✅ 확정 (사용자 Q3: 이번에 포함) · 세부(OR 의미)는 🟡 메인 디폴트
- **결정**: 보드(칸반·리스트·캘린더·간트 공통)의 기존 필터(`useTaskFilter`/`TaskFilters`)에 태그 다중 선택 추가. 선택한 태그 중 **하나라도** 붙은 태스크를 보여준다(OR — 노션 "contains any"). 목록 응답에 `tags`가 이미 실리므로 **백엔드 변경 없음**(클라이언트 필터).

- **영향**: 삭제된 태그가 필터에 선택돼 있으면 `tagDeleted` 수신 시 선택에서 제거. 프론트 착수 시 `useTaskFilter` 구조를 확인해 보고.

## D-017 — 팀 단위 태그 정렬 순서, 태그 관리 모달에서 드래그로 재정렬 (supersedes D-012의 "생성순") (2026-10-19)

- **결정**: `TEAM_TAGS.SORT_ORDER` 추가. 생성 시 팀 최댓값+1(맨 뒤). `PUT /teams/:teamId/tags/order { tagIds }`로 팀 전체 순서를 한 번에 보내고 서버가 트랜잭션으로 1..n 재부여. 요청 집합이 현재 팀 태그 집합과 다르면 409. 태그 목록·칩·필터·선택 모달 모두 이 순서. 소켓 `tagsReordered { tagIds }`.
- **근거**: 이동한 태그 하나만 보내는 방식은 동시 재정렬 시 순서가 꼬이는 경우를 따져야 한다. 태그는 팀당 최대 100개라 전체를 보내도 가볍고, 집합 불일치를 409로 거르면 "내가 보던 목록 기준" 의도만 반영된다. 유니크 제약을 두지 않아 재부여 중 일시 중복이 허용된다.
- **버린 대안**: 이름순 고정 — 사용자 요구 불일치. 분수 순서값(LexoRank) — 100개 규모에 과설계.
