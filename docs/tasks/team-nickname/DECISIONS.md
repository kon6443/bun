# 카카오 닉네임 수집 중단 · 팀 단위 닉네임 — 결정 로그

## D-001 — 요구사항 원문과 기본 방향 (2026-11-12)
- **맥락**: 사용자 요청(2026-11-12)
  - 로그인 시 가져오는 닉네임을 저장 등 사용하지 않고 기본 랜덤값으로 제공
  - 팀즈에서는 닉네임을 팀 단위로 설정 가능
  - 기존 닉네임은 그대로 사용. 신규 가입자는 임의 부여. 팀 닉네임은 처음엔 계정 닉네임을 따라가고, 팀에서 따로 설정하면 그 팀 내부 노출은 팀 닉네임으로. 특정 팀의 모든 이름은 팀 닉네임으로 자동 해석
- **결정**:
  1. 카카오 닉네임: 백엔드가 `kakaoNickname`을 무시한다. DTO 필드는 **optional로 남긴다** — 전역 ValidationPipe가 `forbidNonWhitelisted`라 필드를 지우면 구 프론트 요청이 400이 된다. 프론트가 필드를 뺀 뒤 후속으로 DTO에서 제거
  2. 기존 `USERS.USER_NAME`은 손대지 않는다(일괄 변경 없음). NULL 유저는 기존 폴백 `사용자{id}` 유지
  3. 팀 닉네임은 `USER_TEAMS`(TeamMember)에 nullable 컬럼으로 둔다 — 멤버십 행이 곧 "팀 안의 나"
  4. 해석 순서: 팀 닉네임 → 계정 닉네임 → `사용자{id}`. 팀 컨텍스트 응답·이벤트는 **기존 `userName` 필드에 해석값**을 넣는다(필드 추가 없이 프론트 표시부 약 15곳이 수정 없이 따라감 — 프론트 세션 보고). 설정 UI용 원값은 별도 필드로 준다
- **근거**: WORKLOG 2026-11-12 절(백엔드 13지점·프론트 Q3), `src/common/pipes/global-validation-pipe.ts`
- **버린 대안**: 팀 범위 응답에 `teamNickname` 필드를 따로 추가 — 프론트 15곳 수정·누락 위험
- **영향**: auth·team 모듈, Redis 온라인 해시, 팀 소켓 이벤트, 프론트 로그인·팀 관리 UI

## D-002 — 랜덤 닉네임 형식 · 설정 권한 · 중복 정책 (2026-11-12)
- **맥락**: STATUS Q1~Q3, 사용자 응답(2026-11-12)
- **결정**:
  1. 랜덤 닉네임 = 형용사 + 동물 + 4자리 숫자(예: `용감한수달4821`). 계정 닉네임 상한 20자 안. 유니크 강제 없음
  2. 팀 닉네임은 **본인만** 설정·해제한다(관리자가 타인 것 변경 불가). 활성 멤버만
  3. 같은 팀 안 중복 **허용**(계정 닉네임과 같은 정책)
- **버린 대안**: `사용자{id}`(순번 노출) · 영문 랜덤 · 관리자 대리 변경 · 팀 내 중복 금지(계정 닉네임과 충돌 판정 모호·동시성)
- **영향**: 인가는 "본인 + 활성 멤버" 검증만, 유니크 인덱스 없음

## D-003 — API·소켓 계약과 구현 구조 (2026-11-12)
- **맥락**: D-001·D-002를 코드로 옮기며 정한 계약. 프론트(next-bun-fe)가 이 절을 기준으로 구현한다
- **결정**:
  1. `PUT /teams/:teamId/users/me/nickname` body `{ teamNickname }`(trim 후 1~20자) · `DELETE` 같은 경로로 해제. 둘 다 200 `{ code, data: { teamId, userId, teamNickname, userName }, message }`. 비활성·비멤버 403 `TEAM_FORBIDDEN`, 검증 실패 422 `VALIDATION_ERROR`. 경로에 userId를 받지 않아 "본인만"이 구조로 보장된다
  2. 소켓 `memberNicknameChanged` `{ teamId, userId, userName, teamNickname }`를 room `team-{id}` 전체(본인 포함)에 보낸다. 같은 시점에 Redis 온라인 해시·소켓 매핑의 이름을 "있을 때만" 갱신(Lua) — 그 사이 나간 유저를 되살리지 않는다
  3. `GET /teams/:teamId/users` 항목에 `teamNickname`(원값, nullable) 추가. 팀 범위 `userName`은 더 이상 null이 아니다(태스크·댓글·멤버 목록·역할/상태 변경 응답·이벤트) — 폴백이 `사용자{id}`로 통일
  4. 해석은 `TeamDisplayNameService`(조회) + `getTeamDisplayName`(순수 함수) 한 곳. 이미 USER_TEAMS를 조인한 쿼리(멤버 목록·읽음 상태)는 순수 함수, 나머지는 서비스
  5. 소켓 핸드셰이크 때 읽은 `client.data.user.userName`을 팀 이름에 쓰지 않는다 — joinTeam·chatMessage에서 매번 조회(연결 뒤 닉네임 변경 반영)
  6. 팀을 떠난(비활성) 멤버도 행이 남아 있으면 팀 닉네임을 쓴다 — 지난 태스크·댓글·채팅의 작성자 이름
  7. 알림(텔레그램·디스코드) 역할·상태 변경 제목도 팀 안 표시 이름. 폴백 표기가 `사용자 2` → `사용자2`로 바뀐다
- **근거**: WORKLOG 2026-11-12 "백엔드 구현" 절
- **버린 대안**: `PATCH /teams/:teamId/users/:userId/nickname`(본인 검증 분기 필요) · 해제를 `PUT { teamNickname: null }`로(검증 규칙이 갈라짐) · 소켓에 매번 DB 대신 Redis 이름 읽기(갱신 누락 시 오래 남음)
- **영향**: 프론트 — 로그인 요청에서 kakaoNickname 제거, 팀 닉네임 설정 UI, 이벤트 반영, `TeamUserResponse.teamNickname` 타입

## D-004 — 팀 닉네임은 가입 시점 복사본, 이후 계정 닉네임과 독립 (2026-11-12) — supersedes D-001 결정 4의 "미설정이면 계정 닉네임을 따른다"·D-003 결정 1의 DELETE
- **맥락**: 사용자 지시(2026-11-12) — "마이페이지에서 전체 닉네임을 수정해도 팀즈에 영향이 안 가도록", "회원가입하면 랜덤 계정 닉네임, 팀즈 가입 시 동일하게 팀 닉네임 설정, 추후 팀 단위로 변경". D-001~D-003 구현은 팀 닉네임이 NULL이면 계정 닉네임을 **실시간으로 따라가** 마이페이지 변경이 팀에 번졌다
- **결정**:
  1. 팀 가입 시점(팀 생성 MASTER·초대 수락 신규)에 `TEAM_NICKNAME` = 그때의 계정 표시 이름(`getDisplayName`)을 같은 트랜잭션에서 저장
  2. 재가입(비활성 행 재활성화)은 이 팀에서 쓰던 팀 닉네임을 유지하고, NULL일 때만 복사
  3. 기존 멤버는 마이그레이션 `…074`로 NULL 행만 백필(비활성 포함). down은 no-op(백필값과 사용자 값 구분 불가)
  4. 해제(`DELETE …/users/me/nickname`) 제거 — 되돌릴 "따라가기" 상태가 없다. 변경은 `PUT`만
  5. 읽기 해석(팀 닉네임 → 계정 닉네임 → `사용자{id}`)은 유지 — NULL 행(배포 틈새 등)의 안전망
- **근거**: 가입 경로 grep — USER_TEAMS 행 생성은 `team.service.ts` insertTeam·acceptTeamInvite 두 곳(WORKLOG 2026-11-12 설계 변경 절)
- **버린 대안**: 읽을 때만 해석(마이페이지 변경이 번짐) · 계정 닉네임 변경 시 팀 닉네임 일괄 동기화(요구와 반대) · 백필을 앱 지연 채우기로(읽기 경로에 쓰기 발생)
- **영향**: 프론트 — 해제 UI 없음, 설정 폼 초깃값 `teamNickname ?? userName`(next-bun-fe에 통지 2026-11-12). WORKLOG 리뷰 루프 절 #3("계정 닉네임 변경 실시간 반영" 후속)은 **폐기** — 번지지 않는 것이 정상

## D-005 — 팀 닉네임 편집 진입점: 눈에 잘 띄게, 여러 곳 + 공통 로직 1벌 (2026-11-12)
- **맥락**: 프론트 1차 구현은 팀 관리 섹션 > 멤버 탭 > 내 카드에만 편집기를 뒀다. 섹션이 기본 접힘·기본 탭이 통계라 발견성이 낮다(next-bun-fe 보고)
- **결정**: 사용자 응답(2026-11-12) "최대한 눈에 잘 보이게, 여러 곳에 적용해도 됨, 대신 리팩터를 잘 해 둘 것"
  - 팀 화면 기본 상태(접힘·탭 전환 없이)에서 보이는 진입점을 둔다. 기존 멤버 탭 진입점도 유지
  - 저장·검증·에러 처리·상태는 공통 훅/컴포넌트 1벌로 두고, 진입점은 그것을 재사용만 한다(복붙 금지)
  - 구체 위치는 프론트가 제안·구현하고 메인이 Playwright로 확인
- **영향**: 프론트만. 백엔드 계약 변화 없음

## D-006 — 멤버 목록 응답에 joinedAt 추가 · 팀 관리 탭 버튼 접근 가능한 이름 (2026-11-12)
- **맥락**: 실측 중 발견한 기존 결함 2건(develop 동일). 사용자 지시(2026-11-12): "팀관리 멤버 카드에 백엔드도 응답해서 수정", "탭 버튼 스크린리더 이름, 의도가 명확하면 진행"
- **결정**:
  1. `GET /teams/:teamId/users` 항목에 `joinedAt`(USER_TEAMS.JOINED_AT, nullable 선언 — DB 기본값 SYSTIMESTAMP로 현재 19행 모두 값 있음) 추가. 프론트는 null이면 날짜 대신 대체 표기
  2. 팀 관리 탭 버튼 `aria-label` = "라벨 인원수"(인원수 없는 탭은 라벨) — 시각 변화 없음. 의도가 명확(기존 `title`이 라벨)해 진행
- **근거**: 프론트 `TeamManagementSection.tsx:379`가 `member.joinedAt`을 읽는데 응답에 없음(next-bun-fe 확인), `:289-292` 탭 버튼 aria-label 없음 · `pnpm db:select` JOINED_AT NULL 0/19
- **영향**: API 계약 필드 추가(하위 호환) · 프론트 2파일
