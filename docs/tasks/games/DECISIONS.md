  - 빈도 제한: IP 기준 라우트 스로틀 + 일회용 게임 세션(서버 발급, Redis) 1건당 등록 1회

## D-005 — 리플레이 검증 방식과 서버 부하 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q1 — 리플레이 검증 진행)
- **방식**:
  1. 게임 시작 시 서버가 일회용 세션을 발급한다: `sessionId` + 랜덤 `seed` + 서버 시작 시각(Redis, TTL).
  2. 프론트는 `seed`로 블록 순서를 만들고(같은 seed = 같은 블록 순서), 고정 틱(예: 60틱/초) 단위로 게임을 진행하며 입력(틱 번호 + 동작: 좌·우·회전·소프트/하드 드롭·홀드)을 기록한다.
  3. 게임 오버 시 `sessionId` + 입력 기록 + 이름을 보낸다. **점수는 보내지 않는다**.
  4. 서버는 같은 엔진 코드로 `seed`와 입력 기록을 화면 없이 다시 돌려 점수·줄 수·레벨을 직접 계산하고 그 값을 저장한다. 입력 기록이 불가능한 동작을 담고 있으면 거부한다.
  5. 추가 검사: 리플레이 틱 수(=게임 시간)가 서버가 잰 실제 경과 시간을 넘으면 거부(빨리 감기 봇 차단), 세션은 1회만 사용.
- **서버 부하(추정 — 구현 후 실측)**: 테트리스 시뮬레이션은 10×20 칸 계산이라 틱당 연산이 아주 작다. 10분 게임 = 36,000틱이고 화면을 그리지 않으므로 Node에서 수~수십 ms 수준으로 예상. 하루 1,000건 등록이면 CPU 수십 초. 입력 기록은 수천 건 동작이라 수십 KB 이하. DoS 방지로 최대 틱 수·입력 수·본문 크기 상한을 둔다. 실측이 크면 worker thread로 분리.
- **막는 것 / 못 막는 것**: "API로 99,999,999점 보내기" 같은 위조는 원천 차단(서버가 점수를 계산). 사람처럼 입력을 생성하는 봇(자동 플레이 AI)은 못 막는다 — 실시간 속도 검사로 비용만 높인다.
- **비용**: 엔진(게임 규칙)을 프론트·백엔드가 **똑같이** 실행해야 한다 — 별도 레포라 공유 방식이 필요(복사 + 같은 입력 → 같은 점수를 고정하는 계약 테스트, 또는 별도 패키지). 엔진은 `Math.random`·`Date`·실수 오차를 쓰지 않는 결정적 코드여야 한다. 일회용 세션 + 타당성 검사만 하는 방식보다 규모가 크다(백·프 각각 중 → 대).
- **대안**: 일회용 세션 + 타당성 검사(시간 대비 점수·줄 수 상한) — 단순하지만 그럴듯한 범위의 위조 점수는 통과한다.

## D-006 — 랭킹은 게임 공용 테이블 1개 + GAME_TYPE (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 Q3 — 공용 테이블 진행)
- **맥락**: 사용자 제안 — 테트리스 외 게임도 같은 테이블에 넣고, 계획은 없지만 통계 편의를 위해 합친다.
- **결정(안)**: `GAME_SCORES` 한 테이블에 `GAME_TYPE`(코드값, 예: `TETRIS`)을 두고 모든 게임의 랭킹 기록을 넣는다.
  - **공통 컬럼**: 기록 ID · `GAME_TYPE` · `SCORE`(정수, 순위 기준) · `PLAYER_NAME` · `USER_ID`(로그인 시, NULL 허용) · `DURATION_MS` · `CRTD_AT` · `IS_HIDDEN`(운영자 숨김)
  - **게임별 값**(테트리스의 줄 수·레벨 등)은 `DETAIL` JSON 1컬럼에 둔다 — 게임마다 컬럼을 늘리지 않는다. DB가 **Oracle 19c**(실측)라 네이티브 JSON 타입(21c+)은 없고 `CLOB` + `CHECK (DETAIL IS JSON)`으로 둔다. 통계는 `JSON_VALUE`로 꺼낸다.
  - **인덱스**: `(GAME_TYPE, SCORE DESC)` 전체 랭킹 · `(GAME_TYPE, CRTD_AT)` 일간·주간 랭킹과 통계
  - **정렬 방향**(높을수록 좋음 / 시간 기록처럼 낮을수록 좋음)과 게임 목록은 DB가 아니라 앱 설정(코드)에 둔다 — 새 게임은 코드값 추가 + `GAME_TYPE` CHECK 교체 마이그레이션 1개
  - **리플레이 입력 기록**(Q1에서 채택 시)은 크고 조회에 안 쓰므로 랭킹 테이블에 넣지 않는다 — 검증 후 버리거나, 보관한다면 별도 테이블
- **근거**: 순위 조회·통계·운영 숨김·빈도 제한 로직이 게임과 무관하게 같다 → 테이블·API·화면 컴포넌트를 하나로 재사용. 게임별 테이블은 통계마다 UNION이 필요하다.
- **버린 대안**: 게임별 테이블(스키마는 엄격하지만 게임마다 마이그레이션·API·통계 쿼리 중복) · 게임별 전용 컬럼을 공용 테이블에 계속 추가(NULL 컬럼이 쌓인다)
- **주의**: 같은 `SCORE` 컬럼이라도 게임마다 의미·단위가 다르므로 **게임 간 점수 비교·합산 통계는 의미가 없다** — 통계는 게임별로 낸다.

## D-007 — 낚시는 `/fishing` URL 유지, `/games` 목록에서 진입 (2026-10-21)
- **상태**: ✅ 확정 (메인 판단 — Q2, 프론트 조사 근거. 사용자 이의 시 supersede)
- **결정**: `/fishing` 경로·SEO(canonical·sitemap·JSON-LD)·소켓을 그대로 두고, BNB "낚시" 탭을 "게임"(`/games`)으로 교체한다. `/games` 목록에 테트리스·낚시 카드를 둔다. BNB "게임" 탭은 `/games/**`와 `/fishing/**`에서 활성 표시(`/` 경계로 잘라 `/gamesX` 오탐 방지). 낚시 게임 화면의 "← 나가기"는 `/`에서 `/games`로 바꾼다.
- **근거**: `/fishing` 참조 41곳(도감 개별 URL 색인 포함), redirect 장치 없음 — 이동하면 301 redirect·치환·검색 재평가 위험(비용 중)을 지고 얻는 것은 URL 일관성뿐(WORKLOG 프론트 조사 절).
- **버린 대안**: `/games/fishing` 이동 + 301.
- **함께**: 게임 화면 BNB 숨김을 aria-label 문자열 `<style>`(낚시 layout)에서 BottomNavBar 내부 경로 판정으로 옮긴다 — 테트리스 플레이 화면도 같은 목록에 넣는다(비용 소).

## D-008 — 테트리스 엔진: 결정적 순수 TS, 프론트 원본 (2026-10-21)
- **상태**: ✅ 확정 (Q1 리플레이 검증 확정 → 복사 + 골든 픽스처 계약 테스트)
- **결정(안)**: `next-bun/src/app/games/tetris/engine/`에 React·DOM·`Date`·`Math.random`을 쓰지 않는 순수 TS 엔진. 정수 틱(60/s) + 누산기, `[frame, action]` 입력 로그, 32비트 시드 PRNG + 7-bag, 정수 점수, `ENGINE_VERSION`. 리플레이 검증 여부와 무관하게 이 조건으로 만든다(추가 비용 거의 없음 — 나중에 검증을 붙여도 재작성 불필요).
- **Q1이 리플레이 검증이면**: 백엔드에 엔진 복사본 + 양쪽 동일 골든 리플레이 픽스처(seed·inputs → 점수·줄·보드 해시) 계약 테스트, `ENGINE_VERSION` 불일치는 서버 거부. 별도 패키지·모노레포는 이번 범위에 과함.

## D-009 — 조작·품질 기준: 모바일·PC 키보드 모두, 가이드라인급 (2026-10-21)
- **상태**: ✅ 확정 (사용자 지시: "모바일 및 pc 키보드 모두 고려, 고퀄일수록 좋음") — 세부는 DESIGN §4·§5
- **결정**: 공식 테트리스 가이드라인 수준의 조작감을 기준으로 한다 — SRS 회전 + 벽 킥, 7-bag, 홀드, 다음 블록 5개, 고스트, 락 딜레이(이동·회전 리셋 15회 상한), DAS/ARR(사용자 조정 가능), 소프트·하드 드롭, T-스핀·백투백·콤보 점수, 레벨별 낙하 속도.
  - PC: `e.code` 기준 키 매핑(IME 무관) · 동시 입력(좌/우 + 소프트드롭) · DAS/ARR 엔진 내 처리
  - 모바일: 멀티터치 가상 버튼(Pointer Events, 44px 이상, safe-area) · 이동+드롭 동시 입력 · 진동 피드백(지원 기기) · 줌·스크롤·길게 누르기 차단 · 세로 고정(가로면 안내)
  - 품질: 60fps 캔버스(DPR), 줄 삭제 연출(엔진의 줄 삭제 지연 프레임 안에서만), 일시정지·탭 전환 자동 정지, 개인 최고점, 접근성(키 안내·포커스)
- **제약**: DAS/ARR·락 딜레이·지연 프레임이 점수에 영향을 주므로 **전부 엔진 상태로 계산**하고 리플레이 헤더에 싣는다(서버가 같은 값으로 재현).

## D-010 — 순위는 기록 단위 · IP 해시 저장 · 리플레이 보관 (2026-10-21)
- **상태**: ✅ 확정 (사용자 답변 — Q4·Q5 권장안, Q6은 "적다면 저장" → 용량 추정 후 저장)
- **결정**:
  - Q4 순위는 **기록마다 1줄**(아케이드식). 비로그인은 같은 사람을 식별할 수 없어 "이름당 최고 1줄"이 남의 기록을 합치기 때문
  - Q5 `GAME_SCORES.IP_HASH` = HMAC-SHA256(IP, env `GAME_IP_HASH_SECRET`). 원문 IP는 저장하지 않는다. env가 없으면 NULL(safe default) — 운영자가 도배 기록을 묶어 숨기는 용도
  - Q6 리플레이 입력 기록을 별도 테이블 `GAME_REPLAYS`(gzip BLOB)에 보관 — 엔진 버그 수정 후 재검증, 조작 의심 기록 조사에 쓴다
- **근거(용량)**: WORKLOG 2026-10-21 리플레이 용량 절 — 압축 후 기록당 수 KB, 현재 DB 전체 사용량 8.1MB
- **영향**: DESIGN §1·§1-2, 배포 env 1개 추가(`GAME_IP_HASH_SECRET` — 사용자가 서버·로컬 설정 완료 2026-10-21)

## D-011 — 리플레이 재생: 모든 기록을 누구나 재생 (2026-10-21)
- **상태**: ✅ 확정 (사용자 지시: "리플레이 재생 기능도 만들 수 있으면 만들어줘, 다른 유저 것도 다 확인 가능하도록")
- **결정**: 랭킹의 모든 기록을 비로그인 포함 누구나 재생한다. 공개 API `GET /games/:gameType/scores/:scoreId/replay`(숨김 기록 404) + 프론트 재생기(배속·탐색·키 오버레이). 정본 DESIGN §7
- **근거**: 엔진이 결정적이라(D-008) 저장된 seed + 입력만으로 같은 판이 그대로 재현된다 — 별도 녹화 불필요. 리플레이는 D-010으로 이미 보관한다
- **부수 효과**: 조작 의심 기록을 누구나 눈으로 확인할 수 있다(커뮤니티 검증). 입력 기록 공개는 개인정보가 아니다(이름·점수·입력만, IP 해시는 응답에 없음)
- **제약**: 엔진 버전이 바뀌면 이전 기록 재생에 이전 엔진이 필요 — 1차는 같은 버전만 재생, 버전 업 시 보존 여부 결정

## D-012 — `GAME_REPLAYS`에도 `GAME_TYPE` + 복합 FK로 정합성 강제 (2026-10-21)
- **상태**: ✅ 확정 (사용자 제안에 메인 동의)
- **맥락**: 사용자 제안 — 나중에 다른 게임의 리플레이도 같은 테이블에서 관리.
- **결정**: `GAME_REPLAYS.GAME_TYPE`(NOT NULL, CHECK 코드값)을 둔다. 값 불일치를 막으려고 `GAME_SCORES`에 `UNIQUE (SCORE_ID, GAME_TYPE)`, `GAME_REPLAYS`에 `FOREIGN KEY (SCORE_ID, GAME_TYPE) REFERENCES GAME_SCORES (SCORE_ID, GAME_TYPE) ON DELETE CASCADE`.
- **근거**: `SCORE_ID`만으로도 조인하면 게임 종류를 알 수 있지만, 게임별 리플레이 정리·용량 통계를 조인 없이 할 수 있다. 같은 값을 두 곳에 두면 어긋날 수 있으므로 복합 FK로 DB가 강제한다(앱 규칙에만 기대지 않는다).
- **버린 대안**: `GAME_TYPE` 없이 `SCORE_ID` 조인만(사용자 제안 이전안) · 정합성 강제 없이 컬럼만 추가.
- **보류**: 점수 기록 없는 리플레이(연습 모드 등)는 지금 계획에 없다 — 생기면 `REPLAY_ID` 별도 PK로 바꾸는 마이그레이션을 그때 설계한다.

## D-013 — 리플레이는 랭킹 테이블에 합치지 않는다 (D-012 유지) (2026-10-21)
- **상태**: ✅ 확정 (사용자 지시: "성능이슈 있다면 합치지마")
- **맥락**: 사용자가 `GAME_REPLAYS`를 `GAME_SCORES`에 합치는 안을 물었다.
- **결정**: 합치지 않는다. `GAME_REPLAYS` 별도 테이블 + `GAME_TYPE` + 복합 FK(D-012)를 유지한다.
- **근거**: 합치면 성능 위험이 두 가지 생긴다. ① Oracle LOB 기본값(행 안 저장, 약 4KB 이하)이라 1~5KB 압축 리플레이가 행 안에 들어가 순위·기간 조회가 읽는 블록이 늘어난다. ② TypeORM 기본 조회가 리플레이까지 가져와 랭킹 목록에 리플레이가 딸려 온다. 둘 다 `DISABLE STORAGE IN ROW` + `select: false`로 막을 수 있지만, 설정 하나를 빠뜨리면 바로 성능 문제가 된다. 별도 테이블은 구조적으로 이 위험이 없다.
- **버린 대안**: `GAME_SCORES`에 리플레이 컬럼 추가(+ 위 두 안전장치).

## D-014 — 이름 전용 에러 코드 · 입력 상한 6만 동작 · JSON 본문 300kb · 413 정상화 (2026-10-21)
- **상태**: ✅ 확정 (메인 판단 — 프론트 S3b 질의 근거, 배포 전이라 ENGINE_VERSION 1 유지)
- **맥락**: 프론트 질의 — ① 이름 위반이 `VALIDATION_ERROR`라 리플레이 형식 오류와 구분이 안 됨(이름만 바꿔 재제출할지 판단 불가) ② 입력 2만 동작/60분 = 초당 5.5회라 빠른 플레이어의 30~60분 판(그 사람의 최고 기록)이 상한에 걸림 ③ 413 code 문의
- **결정**:
  - 이름 형식 판정을 DTO에서 서비스(`player-name-policy.ts` `checkPlayerName`)로 옮기고 422 `GAME_PLAYER_NAME_INVALID`(신규)를 쓴다. 금칙어는 기존 `GAME_PLAYER_NAME_FORBIDDEN`. 둘 다 세션 소모 전에 판정 → 같은 세션으로 재제출 가능. 나머지 `VALIDATION_ERROR`는 리플레이·세션 형식(재시도 불가)
  - 입력 상한 `MAX_INPUT_LENGTH` 40,000 → 120,000(동작 6만 = 60분 기준 초당 16.7회). 엔진 원본(프론트) 상수 변경 → 사본 재복사. 배포 전이고 저장된 리플레이가 없어 `ENGINE_VERSION`은 1 유지
  - JSON 본문 한도 100kb → 300kb (`JSON_BODY_LIMIT`, `main.ts`·E2E 헬퍼 공유). 120,000개 이론상 최대 약 262KB(delta 합 ≤ 216,000)
  - **기존 버그 수정**: body-parser 오류(http-errors, `expose: true` 4xx)가 `HttpException`이 아니라 전역 필터에서 500 `INTERNAL_SERVER_ERROR`로 나가던 것을 원래 4xx로 — 413 `PAYLOAD_TOO_LARGE`·400 `BAD_REQUEST`, 메시지는 고정 한국어(원문 비노출). 모든 API에 적용되는 변경
- **근거**: E2E 탐침에서 100kb 초과 본문 → 500 실측(WORKLOG). 실측 최악 리플레이 본문 80.5KB, 이론 최대(4만 개) 약 100KB = 기존 한도의 98%
- **버린 대안**: 이름 오류를 message 문자열로 구분(깨지기 쉬움) · 입력 상한 유지(최고 기록이 등록 불가) · 클라이언트 압축 전송(엔진·서버 양쪽 복잡도)
- **영향**: API 계약 — 신규 code `GAME_PLAYER_NAME_INVALID`, 전역 413·400(기존 500) — 프론트에 전달 완료. 413·400 변경은 기존 화면에 영향 없음(기존에 이 경로로 성공하던 요청 없음 — 본문 100kb 초과·잘못된 JSON은 원래 실패)

## D-016 — D-014 서술 정정: JSON 문법 오류는 원래 400, 이번 변경 대상 아님 (2026-10-21)
- **상태**: ✅ 확정 (리뷰 R2 교차검증 — supersedes D-014의 "400 `BAD_REQUEST`(기존 500)·고정 한국어 메시지" 부분)
- **정정**: body-parser의 JSON 문법 오류는 `SyntaxError`라 Nest(`routes-resolver` `mapExternalException`)가 필터보다 먼저 `BadRequestException(err.message)`로 바꾼다 → 원래부터 400 `BAD_REQUEST`이고 message는 파서 원문(클라이언트가 보낸 본문 일부 — 내부 정보 아님). ## D-017 — JSON 본문 파서는 CORS·helmet 뒤에 등록 (D-014 회귀 수정) (2026-10-21)
- **상태**: ✅ 확정 (리뷰 R5 — Opus·review-flow 두 리뷰어가 독립적으로 같은 결함 지적, 메인 재현)
- **맥락**: D-014에서 `app.useBodyParser('json', ...)`를 `NestFactory.create` 직후에 넣었다. `useBodyParser`는 호출 즉시 미들웨어를 등록하므로 `enableCors`·`helmet`보다 앞에 붙었고(Nest 기본 파서는 `init()` 때 등록돼 원래는 뒤), 파서가 내는 400·413·415 응답에 CORS·보안 헤더가 빠졌다 — 교차 출처 브라우저는 본문을 못 읽어 네트워크 오류가 되고 D-014가 약속한 413 code가 프론트에 닿지 않는다. 모든 JSON 라우트에 해당.
- **결정**: `useBodyParser`를 미들웨어 등록 끝(문서 리다이렉트 뒤, `setGlobalPrefix` 앞 — 기본 파서와 같은 위치)으로 옮기고 순서 이유를 주석으로 남긴다.
- **근거**: 최소 앱 재현(scratchpad `cors.cjs`) — 앞 등록: `400/413 ACAO=undefined CSP=false` · 뒤 등록: `400/413 ACAO=http://localhost:3000 CSP=true`. E2E 헬퍼는 CORS·helmet을 재현하지 않아 E2E로는 잡히지 않는다 → 실서버 Origin 헤더 확인으로 검증
