## 2026-10-24 — 계약 질문에 기억으로 답했다가 DTO 변환을 놓쳤다

- **실패 양상**: 프론트 질문 "제출 응답에 서버가 정규화한 이름을 넣을 수 있나"(games-polish Q-S2)에 "서버는 이름을 검사만 하고 정규화하지 않는다"고 답했다. 실제로는 제출 DTO의 `@Transform(normalizePlayerName)`이 앞뒤 공백 제거·연속 공백 1개로 정리해 저장한다. 실API 검증 스크립트를 쓰려고 DTO를 열었을 때 Swagger 설명("…정리 후 1~12자")을 보고 알았다.
- **탐지 신호**: 계약 답에 `파일:라인 + 인용`이 없다 · 서비스 코드만 보고 "변환 없음"이라고 판정한다 · 요청 DTO에 `@Transform`이 있을 수 있는 필드(이름·코드·문자열)다.
- **근본 원인**: 서비스(`checkPlayerName`은 검사만)만 떠올리고, 값이 서비스에 닿기 전 DTO 단계 변환을 확인하지 않았다. 프론트에는 `파일:라인 + 인용`을 요구하면서 메인 답에는 근거를 붙이지 않았다.
- **예방 규칙**: 프론트 계약 질문에 답할 때도 `파일:라인 + 인용`을 붙인다. 요청 필드의 "서버가 받는 값"은 DTO의 `@Transform`·전역 ValidationPipe(`transform: true`)까지 따라가 확인한다.

## 2026-10-23 — 호출처 grep 결과를 `head`로 잘라 E2E 호출처를 빠뜨렸다

- **실패 양상**: 대전 `lock()` 입력 시그니처에 필드를 추가하면서 `grep -rn "\.lock(" src test | … | head`로 호출처를 확인했다. 출력 10줄이 단위 스펙으로 꽉 차서 `test/*.redis.e2e-spec.ts`의 호출 20여 곳이 보이지 않았다. `ci:core`(단위)는 통과했고, E2E에서 TS 컴파일 오류로 스위트 2개가 실패해서야 알았다(games-polish P1 BT-01).
- **탐지 신호**: "변경 심볼 전수 확인" 명령에 `head`·`| head -N`이 붙어 있다 · 출력 줄 수가 정확히 N이다 · E2E는 `ci:core`에 없다.
- **근본 원인**: 탐색용 습관(`head`로 출력 줄이기)을 판정용 grep에 그대로 썼다. 잘린 출력은 "이게 전부"와 구별되지 않는다.
- **재발(2026-10-24)**: 대전 `garbageLog` 반환 타입에 `from`을 추가하면서 이번에는 호출처 grep 자체를 건너뛰었다 — 단위는 통과, E2E 2곳(대역 구현 타입·실제 Redis 기댓값)에서 드러났다. 반환 타입 변경도 시그니처 변경이다.
- **예방 규칙**: 함수의 인자·**반환 타입**을 바꾸면 편집 전에 `grep -rln <이름> src test`로 호출처·대역(mock) 목록부터 만든다. 호출처 grep은 `head` 없이 돌리고, 많으면 `| wc -l`로 개수를 먼저 본 뒤 파일별(`-l`)로 나눠 읽는다. 시그니처를 바꾸면 `ci:core` 뒤에 해당 모듈 E2E(`pnpm test:e2e --testPathPatterns <모듈>`, sandbox 밖)까지 돌린다.

## 2026-10-22 — 간헐 E2E 실패를 "환경 문제"로 넘기고 원인을 안 남겼다

- **실패 양상**: E2E가 실행마다 다른 테스트 1~3건씩 실패했다(407 Proxy Authentication Required · 엉뚱한 404). 여러 슬라이스 동안 "프록시 환경 문제·미재현"으로만 기록하고 넘어갔다. 원인은 테스트 서버가 `listen(0)`(supertest 기본)으로 `::`에 열리는 것이었다 — macOS는 다른 프로세스(다른 Claude 세션의 로컬 프록시 등)가 `127.0.0.1`로만 점유한 포트도 `::`로 내주고, supertest는 `127.0.0.1:포트`로 요청해 그 프로세스에 닿는다.
- **탐지 신호**: 실패 테스트가 실행마다 바뀐다 · 응답 상태가 앱이 낼 수 없는 값(407)이다 · 실패 메시지를 남기지 않은 채 "재실행하니 통과"로 판정하려는 순간.
- **근본 원인**: 실패 로그를 보존하지 않고 재실행 통과로 판정했다. 앱이 낼 수 없는 상태코드(407)를 "환경"으로 분류하고 그 환경이 어떻게 요청을 가로채는지 확인하지 않았다.
- **예방 규칙**: 간헐 실패는 **반복 실행하면서 로그를 파일로 남기고** 실패 메시지부터 본다. 앱이 낼 수 없는 응답이면 요청이 어디로 갔는지(바인딩 주소·포트·프록시)를 재현으로 확인한다. E2E 서버는 `listen(0, '127.0.0.1')`로 클라이언트와 같은 주소에 연다(`test/helpers/e2e-app.ts`). 근거: 수정 전 전체 E2E 8회 중 3회 실패 → 수정 후 15회 연속 통과, `::` 바인딩 + `127.0.0.1` 점유 포트 재현으로 407 확인.

## 2026-10-22 — 변이 검사로 코드를 잠시 바꾼 사이 병렬 리뷰어가 그 파일로 테스트를 돌렸다

- **실패 양상**: 디펜스 B1-a 리뷰 6라운드에서 메인이 `verify-worker-pool.ts`의 가드를 일부러 지운 변이 검사(`sed`로 수정 → jest → 원본 복원)를 하던 몇 초 사이에, 백그라운드 Opus 리뷰어가 같은 작업 트리로 테스트를 돌려 "1건 실패"를 봤다. 리뷰어가 파일 내용(`if (true)`)과 6초 뒤 복원을 직접 확인해 오탐으로 걸렀지만, 확인하지 않았다면 존재하지 않는 결함을 지적하거나 메인이 그 지적을 고칠 뻔했다.
- **탐지 신호**: 병렬 서브에이전트(리뷰어·조사자)가 같은 worktree에서 테스트·파일 읽기를 하는 중에, 메인이 같은 파일을 임시로 바꾸는 검증(변이 검사·실험 수정)을 시작한다.
- **근본 원인**: 변이 검사는 "잠깐 바꿨다 되돌린다"는 전제라 원자적이지 않고, 같은 작업 트리를 보는 다른 에이전트에게는 일시 상태가 그대로 보인다.
- **예방 규칙**: 같은 worktree에서 리뷰어·조사 에이전트가 돌고 있으면 변이 검사를 하지 않는다 — 리뷰 결과를 받은 뒤 하거나, 파일을 바꾸지 않는 방식(복사본 디렉토리에서 실행, 테스트에서 의존성 주입으로 변이)을 쓴다. 리뷰어 지시에는 "실패를 보면 파일 상태부터 확인"을 넣는다.

## 2026-10-20 — dev 서버가 도는 디렉토리에서 `next build`를 돌려 dev가 500이 됐다

- **실패 양상**: 프론트 worktree에서 `pnpm dev`가 실행 중인데 같은 디렉토리에서 `pnpm build`로 검증했다. 이후 Playwright가 타임아웃 — dev가 `ENOENT …/.next/static/development/_buildManifest.js.tmp…`로 500을 내고 있었다.

- **근본 원인**: `next dev`와 `next build`가 같은 `.next` 디렉토리를 쓴다. build가 dev 산출물을 덮어썼다(dev 종료 → `.next` 삭제 → 재기동으로 복구·재현 확인).

## 2026-10-20 — Playwright `setOffline`으로 소켓 재연결을 시험해 "복구 안 됨"으로 오판할 뻔했다

- **실패 양상**: "초기 조회 실패 후 소켓 재연결 시 자동 복구"를 `context.setOffline(true→false)`로 시험해 실패로 나왔다. 백엔드 프로세스를 실제로 재시작해 소켓을 끊자 정상 복구됐다(소켓 close→open 로그로 확인).
- **탐지 신호**: 재연결이 전제인 시험에서 소켓 close/open 이벤트를 관찰하지 않았는데 "복구 안 됨"이 나왔다.
- **근본 원인**: Chromium 오프라인 에뮬레이션은 이미 열린 WebSocket을 끊지 않는다 — 재연결 자체가 일어나지 않았다.
- **예방 규칙**: 재연결 시험은 서버 프로세스 재시작(또는 서버 측 강제 disconnect)으로 하고, `page.on('websocket')`으로 close→open을 함께 기록해 전제가 성립했는지 먼저 확인한다.

## 2026-10-07 — 잘린 검증 출력을 보고 "문서 수치가 낡았다"고 잘못 보고했다

- **실패 양상**: 코드 규약 분할 중 근거를 일괄 실측하는 헬퍼가 출력마다 `head -3`을 걸었는데, 그 3줄을 전수로 읽고 "트랜잭션 4곳 → 실제 3곳", "QueryBuilder 수치 불일치"라고 사용자에게 보고했다. 감사 에이전트가 4곳·5건으로 반증했다. 규약 본문에는 개수를 쓰지 않아 내용 피해는 없었다.
- **탐지 신호**: 개수를 셀 때 `wc -l`이 아니라 목록 출력을 눈으로 셌다. 출력 헬퍼에 `head`·`cut`이 걸려 있다.
- **근본 원인**: "표시용으로 자른 출력"과 "판정용 전수 출력"을 같은 명령으로 겸했다.
- **예방 규칙**: 개수·존재 판정은 `| wc -l` 또는 `-c`로 따로 센다. 출력을 자르는 헬퍼의 결과로는 "없다/줄었다"를 판정하지 않는다.

## 2026-09-23 — `git add` 실패 뒤에도 커밋이 실행돼 내용이 빠진 커밋이 생겼다

- **실패 양상**: 프론트 refactor 커밋에서 `git add <이미 rename 스테이징된 옛 경로> …; git diff --cached --stat; git commit …`을 실행했다. 옛 경로가 pathspec에 안 맞아 `git add` 전체가 실패했는데, `;`로 이어져 있어 커밋이 그대로 진행됐다 → 이름 변경 2건만 담긴(내용 0줄) 커밋이 생겼다.
- **탐지 신호**: 출력 첫 줄 `fatal: pathspec '…' did not match any files`, 그리고 `--stat`이 `0 insertions(+), 0 deletions(-)`.
- **근본 원인**: 스테이징과 커밋을 **실패해도 계속 가는 `;`** 로 이었다. 스테이징 결과를 사람이 확인하기 전에 커밋까지 한 번에 보냈다.
- **예방 규칙**: 스테이징 → 커밋은 `&&`로만 잇거나, **스테이징과 커밋을 별도 호출로 나눠 `--stat`을 확인한 뒤 커밋**한다. push 전이면 `git reset --soft`로 풀고 다시 만든다(이번엔 사용자 승인 후 그렇게 복구 — 원격 영향 없음).

## 2026-09-23 — 권한 deny 규칙을 끝이 `:*`인 모양으로 써서 마이그레이션 차단이 무효였다

- **실패 양상**: 프론트 `.claude/settings.json`에 `Bash(npm run db:migrate:*)`·`Bash(npm * db:migrate:*)`를 넣었는데, headless 세션 탐침에서 `npm run db:migrate:fake-probe`가 **그대로 실행**됐다. 같은 파일의 `Bash(pnpm db:migrate:up*)`는 막혔다. 같은 조사에서 백엔드도 `pnpm run db:migrate:up`·`pnpm --dir . …`이 deny를 빠져나가는 것을 확인했다(`pnpm db:migrate:up*`만 있었다).
- **탐지 신호**: 존재하지 않는 스크립트명(`…-probe`)으로 실행했을 때 권한 거부가 아니라 `Missing script`가 나온다.
- **근본 원인**: ① 끝이 `:*`인 규칙은 옛 접두사 문법으로 해석돼 `db:migrate` 뒤에 `:fake…`가 이어진 명령을 못 잡는다(실측, 해석 규칙 자체는 추정) ② 패턴을 "스크립트명 바로 앞이 `pnpm`"인 한 가지 모양만 썼고, 중간에 `run`·`--dir`이 끼는 형태를 시험하지 않았다. 규칙을 쓰고 **실제로 막히는지 시험하지 않았다**.
- **예방 규칙**: deny 패턴은 끝을 `…up*`처럼 글자 뒤 `*`로 쓰고 `:*`로 끝내지 않는다. 중간 토큰이 끼는 형태(`pnpm run`, `pnpm --dir x`, `npm --prefix x run`, `cd x && …`)를 함께 넣는다. **추가한 deny는 반드시 탐침으로 시험한다** — 실존하지 않는 스크립트명을 쓰면 규칙이 빗나가도 `Missing script`로 끝나 안전하다. 실제 스크립트명으로 시험하지 않는다(`Bash(pnpm:*)`가 allow라 빗나가면 곧 상용 적용).

## 2026-08-12 — 로컬 빌드 성공이 Docker 빌드 성공을 뜻하지 않는다

- **예방 규칙**: 빌드 **진입 설정**(`tsconfig*.json`, `build` 스크립트, 엔트리 경로)을 바꾸면 같은 커밋에서 `Dockerfile`의 `COPY` 목록을 확인한다. 검증은 Docker 없이도 가능하다 — 임시 디렉토리에 `COPY` 목록만 복사하고 `node_modules`를 심볼릭 링크한 뒤 빌드 명령을 돌리면 CI 실패를 그대로 재현할 수 있다. `pnpm ci:all`은 이 종류를 잡지 못한다(레포 전체를 입력으로 쓰므로).
